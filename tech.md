## 1. Продукт

KERBEROS: скрипт защиты VPN-серверов для владельцев панели Remnawave. Ставится на сервер панели одной командой после `git clone`. Сам находит панель, просит разрешения, проверяет ноды и ставит меры защиты на выбранные.

Для кого: владельцы VPN-сервисов и селфхостеры на Remnawave, от 1 до 50 нод. Большинство не администраторы: заходят на серверы по паролю, держат Reality с чужим SNI, не знают, как выглядит блокировка ТСПУ со стороны сервера.

Цель: массовое использование. Человек не выходит из окна скрипта: не правит файлы, не ходит в панель, не копирует ключи руками. Всё, что нужно ввести, вводится в окне; всё, что изменилось, остаётся в отчёте и откатывается одной командой.

Что делает:
1. **Проверка.** Читает панель и ноды, не меняя их настроек (на ноды ставится только агент для чтения фактов), и показывает красный отчёт: что не так, чем грозит, что из этого KERBEROS исправит сам.
2. **Исправление.** Показывает план по нодам, спрашивает разрешение, применяет меры по одной с бэкапом и проверкой, выдаёт зелёный отчёт: что изменилось на каждой ноде, новые порты SSH и отпечатки ключей, бэкапы и как откатить.
3. **Откат.** Возвращает любой прошлый запуск целиком или по одному изменению.

Видео для запуска открывается красным отчётом «Проверки» и заканчивается зелёным отчётом после «Исправления» (§12.4).

## 2. Принципы UX

1. **Всё в окне.** Логин панели, пароль первичного входа на ноду, домен для self-steal, разрешение на изменения вводятся в окне KERBEROS. Человеку не нужен браузер, второй терминал и редактор. Единственное исключение: API-токен Remnawave создаётся в панели один раз, в браузере (§7.3); дальше KERBEROS хранит его сам.
2. **Ничего без разрешения.** «Проверка» не меняет настроек ни в панели, ни на нодах: она только ставит на ноды агента и ключ для чтения фактов и говорит об этом на S4. «Исправление» показывает план и меняет что-либо только после явного подтверждения на экране согласия (§6, S7).
3. **Красное и зелёное.** Находка показана цветом риска, одной строкой «что не так» и одной строкой «чем грозит». Подробности по нажатию.
4. **Простой русский.** Без жаргона в основном тексте: «вход по паролю» вместо `PasswordAuthentication`. Технические имена видны в подробностях и в файле отчёта.
5. **Ничего не теряется.** Каждый шаг пишет бэкап до изменения, проверяет результат после и откатывается сам при ошибке. Прерывание на любом шаге не оставляет ноду наполовину изменённой (§11.5).
6. **Не запереть человека.** Изменения доступа (SSH) применяются с таймером автоотката и подтверждаются новым соединением. Вход по паролю выключается, только когда у человека есть рабочий ключ (§8.5).
7. **Маскировка.** Клавиша `m` и флаг `--mask` заменяют адреса и домены на экране и в отчёте на стабильные значения из диапазонов для документации: и имена из панели, и их DNS-зоны, и имена, которые видны только на нодах (`server_name` nginx, домены certbot, имена в сертификатах). Скриншоты и видео снимаются только так.
8. **Демо.** `--demo` запускает весь сценарий на встроенном парке без панели и серверов. Нужен для разработки, тестов и записи видео без чужой инфраструктуры.

## 3. Стек

| Что | Решение | Почему |
|---|---|---|
| Язык | Python 3.9+ (Ubuntu 22.04: 3.10, 24.04: 3.12, 26.04: 3.14; Debian 12: 3.11, 13: 3.13) | есть на серверах из коробки; запуск без сборки |
| TUI | Rich, вендорённый в `vendor/` с зависимостями, версии закреплены | красивый вывод без `pip`; Ubuntu 24.04 запрещает системный `pip install` |
| Клавиатура | `termios`, `tty`, `select` из стандартной библиотеки | Rich не читает клавиши; виджеты §14 свои |
| HTTP к панели | `urllib.request` | без зависимостей |
| SSH к нодам | системные `ssh`, `ssh-keygen`, `ssh-keyscan` (пакет openssh-client есть на каждом сервере) | готовый проверенный клиент, ControlMaster |
| Агент на ноде | один файл Python 3.9+, только стандартная библиотека | нечего ставить на ноду, кроме одного файла |
| Тесты (только для разработки) | pytest, Hypothesis, ruff | в рантайм не попадают |
| ОС сервера панели и нод | Ubuntu 22.04, 24.04, 26.04; Debian 12, 13 | меры проверены на парке на Ubuntu 24.04 и 26.04; остальные ОС проверяются на стенде (§17) |

Вендоринг: `tools/vendor.py` скачивает Rich и его чисто-питоновые зависимости (`pygments`, `markdown-it-py`, `mdurl`, `typing_extensions` для Python ниже 3.11) закреплённых версий, кладёт их в `vendor/` с лицензиями и пишет `vendor/VERSIONS`. Тест K0 запускает KERBEROS как `python3 -I -S` с одним `vendor/` в пути: без site-packages всё должно работать. Если какой-то пакет из списка не нужен используемым модулям Rich, его можно не вендорить: решение фиксируется в `vendor/VERSIONS` в задаче K0.

### 3.1 Особенности ОС

Различия, которые меняют поведение KERBEROS и агента. Каждое покрыто тестом на стенде своей ОС (§17).

| | Ubuntu 22.04 | Ubuntu 24.04 | Ubuntu 26.04 | Debian 12 | Debian 13 |
|---|---|---|---|---|---|
| Python | 3.10 | 3.12 | 3.14 | 3.11 | 3.13 |
| OpenSSH | 8.9 | 9.6 | 10.x | 9.2 | 10.0 |
| Порт SSH задаёт | `sshd_config` | `ssh.socket` | `ssh.socket` | `sshd_config` | `sshd_config` |
| sudo | sudo | sudo | sudo-rs | sudo | sudo |
| coreutils | GNU | GNU | uutils (Rust) | GNU | GNU |
| Журнал для fail2ban | journald | journald | journald | journald | journald, без rsyslog |

Правила:
- Порт SSH агент меняет по факту, а не по версии ОС: `facts.ssh.socketActivated` (`systemctl is-active ssh.socket` и наличие `ListenStream`) решает, писать drop-in сокета или строки `Port`.
- Агент не полагается на флаги coreutils: файлы, права, время и хэши он считает средствами Python, внешние команды вызывает только для `sshd`, `systemctl`, `nft`, `sysctl`, `ssh-keygen`, `apt-get`, `certbot`, `nginx`, `docker`, `ufw` и `ss`, `ip` из iproute2. Конфиги fail2ban и nginx он читает как файлы.
- Launcher перезапускает себя через `sudo -- "$0" "$@"` без дополнительных флагов: sudo-rs на Ubuntu 26.04 поддерживает не все флаги классического sudo.
- fail2ban всегда с `backend = systemd` и пакетом `python3-systemd`: на Debian 13 нет `/var/log/auth.log`.
- Rich и его зависимости закреплены на версиях, которые работают от Python 3.9 до 3.14; `tools/check.sh` проверяет обе крайние версии.

## 5. Установка и запуск

### 5.1 Установка

```bash
git clone https://github.com/<owner>/kerberos.git /opt/kerberos
sudo /opt/kerberos/kerberos
```

Больше ничего. Никаких `pip`, `apt` и загрузок при установке. Обновление: `git -C /opt/kerberos pull`.

### 5.2 Launcher `./kerberos`

1. Если не root: перезапускает себя через `sudo -- "$0" "$@"` с пояснением одной строкой (§3.1). Если задан `SSH_AUTH_SOCK` (человек подключился с `ssh -A`), он передаётся через `sudo -- env SSH_AUTH_SOCK=… "$0" "$@"`: sudo его сбрасывает, а без него S4 не войдёт на ноды, которые пускают только по ключу (§8.2).
2. Ищет `python3` версии 3.9 и выше. Нет: объясняет и предлагает `apt-get install -y python3` после подтверждения (единственная возможная установка пакета на сервере панели).
3. Без TTY запускает только `report` и `finalize`; для остальных команд пишет «Запустите KERBEROS в терминале». Проверяет это уже Python (`__main__`), чтобы текст жил в `copy.py`.
4. `exec python3 -I -S` с `<repo>/src` и `<repo>/vendor` первыми в `sys.path` и запуск `kerberos.__main__`. Пути launcher кладёт в `sys.path` сам: под `-I` Python не читает `PYTHONPATH`.

### 5.3 Команды

| Команда | Что делает |
|---|---|
| `kerberos` | меню: Проверка, Исправление, Откат, Отчёты |
| `kerberos check` | сразу режим «Проверка» |
| `kerberos fix` | сразу режим «Исправление» |
| `kerberos rollback [runId]` | откат запуска или отдельных изменений |
| `kerberos report [runId]` | показать отчёт; без TTY печатает `report.md` |
| `kerberos finalize [runId]` | завершить отложенные шаги (§10.4, шаг 6); без TTY работает по сохранённому токену из опции таймера |
| `kerberos ssh <нода>` | войти на ноду с сервера панели ключом администратора (§8.5) |

Флаги: `--demo`, `--mask`, `--no-color` (также переменная `NO_COLOR`), `--panel remnawave|3x-ui` (панель без вопроса в S2, §7.6), `--help`, `--version`.

Коды выхода: `0` готово; `2` неверные аргументы; `3` нет доступа к панели; `4` часть изменений не применилась и откачена; `5` откат не удался, нужна ручная проверка (отчёт говорит, что именно); `130` прервано пользователем, незавершённые изменения откачены. Если подходят несколько, выигрывает `5`, затем `130`, затем `4`. Меню S1 при выходе возвращает последний ненулевой код своих сценариев; выход клавишей `q` на S9 сохраняет код запуска.

### 5.4 Состояние на сервере панели

`/var/lib/kerberos/` (0700, root):

|---|---|

## 6. Сценарий в окне

Экраны идут по порядку; `Esc` возвращает на шаг назад, пока ничего не изменено.

Области (K23): на S6, в плане S7, на экране согласия и на S9 меры и проблемы сгруппированы одинаково и называются простыми словами: «Свой домен» (self-steal и резерв), «Вход на серверы» (ключ администратора, вход только по ключу, fail2ban, ключи сервера, порт SSH), «Дыры для сканеров» (MPTCP, API ноды, лишние порты, вход в панель), «Туннель за CDN» (фильтр CDN, паддинг и GET у XHTTP), «Подписка» (шаблоны, ping-type, fingerprint), «Наблюдение» (сборщик признаков блокировки). Блоки рисуются рамками; заголовок блока несёт символ и слово (✓, ✎, ✗, ⚠, i), поэтому читается и без цвета.

**S1. Заставка и режим.** Логотип, одна фраза о продукте, меню «Проверка», «Исправление», «Откат», «Отчёты». Если есть незавершённые отложенные шаги (§10.4), сверху плашка «Есть незавершённое: убрать старое имя у {n} нод» (числительные согласуются: `{n:ноды|нод|нод}` в `t()`) с переходом в `finalize`. Пункт финализации в меню: «Завершить переход на свой домен: убрать старые имена». Окно выхода называется «Выход».

**S2. Панель.** Сначала выбор панели этого сервера: Remnawave или 3x-ui, найденная стоит первой (§7.6). Для Remnawave KERBEROS сам ищет её на этом сервере (§7.1) и показывает: где нашёл, версию, адрес API. Дальше вход по API-токену (§7.3): если сохранённый токен подходит, экран ничего не спрашивает (в «Исправлении» сначала предлагает оставить или заменить токен, данный для «Проверки»); иначе просит токен (поле скрыто) и объясняет, где его создать и какие права дать для выбранного режима. Итог: «Панель подключена: {version}, нод {n}, хостов {m}». Если адрес введён руками или версия неизвестна, вместо «Нашёл …» экран пишет «Панель Remnawave по адресу {api}» (для 3x-ui — «Панель 3x-ui по указанному адресу»). Ошибки говорят, что делать: подождать минуту и нажать Enter, проверить, что контейнер панели запущен.

**S3. Ноды.** С 3x-ui экрана нет: нода одна, этот сервер (§7.6). Таблица нод панели: страна, имя, адрес, статус в панели, пользователей онлайн, протоколы, «основа/резерв». Пробел отмечает, `a` отмечает все, Enter дальше. Выключенные ноды видны серыми и не выбираются.

**S4. Доступ к нодам** (на 3x-ui «Доступ к этому серверу»). В «Проверке» экран сначала один раз за запуск объясняет, что KERBEROS поставит на ноды агента и ключ, а настройки SSH, фаервола и VPN не меняет (`access.intro`); Enter дальше, Esc назад, пока ничего не поставлено. Для каждой выбранной ноды, у которой ещё нет доступа KERBEROS (§8.2):
- показывает отпечаток ключа хоста и просит подтвердить; подсказка говорит, где его сверить (консоль хостера, `ssh-keygen -lf …`), а если такой же ключ у другой ноды, вопрос об этом говорит. Изменившийся ключ показан вместе с прежним («Был: …»), предупреждение называет перехват соединения, и по умолчанию выбран пункт «Пропустить ноду»;
- если на порту 22 ключа хоста не видно, спрашивает порт SSH (по умолчанию 22);
- пробует войти ключами root сервера панели и ключом, проброшенным через `ssh -A`; если не вышло, передаёт терминал `ssh`: человек вводит пароль ноды в том же окне, KERBEROS его не видит и не хранит. Нода, которая на вход ключом пароль не предлагает, пароль и не спрашивает: «нет доступа: пускает только по ключу», а под таблицей сказано, что нужно подключиться к серверу панели с `ssh -A` и запустить KERBEROS снова (`access.key_only.hint`, `access.key_only.hint.agent`);
- ставит агента и ключ KERBEROS, проверяет новый вход ключом;
- в «Исправлении» спрашивает про ключ администратора (§8.5) при каждом входе на экран, с прежним ответом по умолчанию.
Подвал вопросов называет Esc: «пропустить ноду» или «пропустить». При многих нодах таблица показывает окно строк («строки a–b из n»), чтобы вопрос всегда помещался. Нода без доступа остаётся в списке с пометкой «нет доступа» и проверяется только со стороны панели.

**S5. Проверка.** Прогресс по нодам (до 4 параллельно, только чтение): факты агента, снимок панели, внешние проверки с сервера панели. Внешний whois для AS запускается, только если человек разрешил это на экране (§10.2, тема 1).

**S6. Отчёт проверки (красный).** Оценка защищённости 0–100 (§12.2) со сводкой, под ними блоки (K23). Одна проблема на всех её нодах — одна строка; находки парка `fleet.same_asn`, `fleet.same_24` и `fleet.shared_hostkey` — строка на группу нод (одна страна и AS, цепочка соседних /24, один ключ). Блок «✓ Исправит KERBEROS» — строка на область: риск самой опасной её проблемы, область, что не так в нескольких словах (первые три и «и ещё N»), где (до трёх нод по имени, больше — числом, затем панель, хосты, шаблоны). Блок «✎ Сделать вам» — строка на проблему, которую KERBEROS сам не исправит: риск, что не так, где, что сделать. Пояснения (риск «инфо»: что KERBEROS сознательно не меняет) — одна строка блока «i Пояснения». Пробел открывает под строкой проблемы области с тем, чем они грозят; у проблемы — чем грозит и подробности; у пояснений — их список. Сводка считает строки: «Найдено проблем: N, из них с высоким риском: H.», «✓ KERBEROS исправит сам: A · после исправления: до X» (оценка, если все исправления KERBEROS пройдут), «✎ Вам вручную: M»; в «Проверке» под ней «f — перейти к исправлению». ↑↓ ходят по строкам всех блоков, `PgUp`/`PgDn`/`Home`/`End` листают; в терминале ниже 30 строк оценка занимает одну строку; путь к отчёту стоит отдельной строкой. `Esc` возвращает к S4 без нового сбора и без повторного вопроса про whois. В режиме «Проверка» здесь конец: отчёт сохранён, путь показан. Клавиша `f` продолжает в «Исправление» на тех же данных: вопрос про ключ администратора (§8.5), новый запуск `fix` с теми же находками, S7.

**S7. План и согласие (только «Исправление»).** Два блока (K23). «KERBEROS сделает сам» — строка на группу мер: «Вход на серверы», «Новый порт SSH», «Дыры для сканеров», «Вход в панель», «Туннель за CDN», «Подписка», «Наблюдение» (группа видна, только если в ней есть что делать). В строке отметка на всю группу ([✓] всё, [ ] ничего, [~] часть и «k из n»), меры группы в нескольких словах и где. Пробел у группы отмечает все её строки, которые могут идти сейчас, или снимает их; строки, ждущие ввода, он не отмечает и говорит, чего они ждут. → раскрывает группу по нодам: строка на меру и ноду со своей отметкой и заметкой; ← сворачивает. «Свой домен вместо чужого сайта» — строка на ноду: домен (или «d: ввести домен»), DNS («DNS ✓», «… ждёт DNS», «нужен домен» или «недоступно»), нужная A-запись, пока DNS не совпал, потом резерв. По умолчанию отмечены все автоматические исправления высокого и среднего риска, кроме `ssh.port` (его человек отмечает сам) и строк, ждущих ввода. `a` отмечает все доступные строки, кроме `ssh.port` и строк, ждущих ввода; повторное `a` снимает эти отметки. Курсор доходит и до недоступных строк; под блоками подробности текущей строки: у группы из нескольких мер — где она и сколько отмечено, её предупреждение; у меры и домена — полное название, домен, DNS, резерв, сети, причина недоступности или нужная DNS-запись, предупреждение. Подвал показывает клавиши текущей строки, `?` — справку экрана; на 3x-ui клавиш `r`, `e`, `u` и `f` нет. Мерам, которым нужен ввод, клавиша работает и в их строке, и в строке группы: сети CDN для `cdn.edge_only` — `e` (§10.6), логин и пароль портала — `p`; домен для self-steal — `d` в строке ноды блока «Свой домен» (§10.4), там же превью сайта-заглушки, клавиша `g` даёт другой сайт, а `u` — выбор сквадов, когда ни один сквад не держит инбаунды ноды и сквадов в панели несколько (строка тогда показывает «u: выбрать сквады» и ждёт выбора, §10.4). Резерв — клавиша `r` в строке основной ноды: «Без резерва» или выбор другой ноды из панели (§10.9); от выбора зависит шаблон подписки. Предупреждения показываются до согласия дословно из §15: перезапуск Xray панелью, новый порт SSH, выключение старых хостов. Несколько новых портов SSH дают одно предупреждение (`fix.ssh_port.warning.many`); на 3x-ui вместо `fix.self_steal.warning` показывается `fix.xui_steal.warning`, без `fix.profile.warning` и `fix.mount.warning`. Строка про финализацию видна, только когда отмечен «Свой домен». Экран согласия (K23): блок «Что изменится» — строка на область с мерами и их нодами (новые порты SSH и закрываемые порты названы, у «Своего домена» — домены и свои профили нод), блок «⚠ Важно знать» — предупреждения §15 пунктами, дословно, под ними «Всё изменённое сохраняется в бэкап и откатывается одной командой.»; длинный список прокручивается (`↑↓`, `PgUp`/`PgDn`, `Home`/`End`), кнопка «Разрешаю изменения» и подсказка закреплены внизу. Enter разрешает, любая другая клавиша возвращает к плану. Тот же экран согласия у отката и финализации. Строки `panel.portal` и `xui.panel_hide` (§10.10) по умолчанию не отмечены и `a` их не отмечает; у строки портала логин и пароль вводятся клавишей `p`.

**S8. Применение.** Доска прогресса: ноды по строкам, шаги текущего исправления по колонкам: бэкап, применение, проверка, подтверждение. Ошибка шага откатывает это изменение и идёт дальше; причина видна строкой под доской и в отчёте. Изменения доступа ждут подтверждения новым соединением (§11.3). `Ctrl+C` спрашивает «Прервать?»: Enter прерывает, Esc продолжает; итоговый экран тогда называется «Прервано». Портал перед панелью и новая ссылка 3x-ui ждут, пока человек войдёт по ней из браузера (§10.10).

**S9. Отчёт исправления (зелёный).** Закреплённый верх: оценка до и после, «Применено {ok} из {total}», что не применилось и что не откатилось, «Осталось проблем: P · исправит следующий запуск: A · вручную: M», ноды без доступа; блок «⚠ Сохраните: новые адреса входа» — строка на ноду с новым портом SSH и командой входа («nl-1: ssh -p … root@…»), новая ссылка на панель (§10.10), ноды со сменённым ключом сервера («ssh-keygen -R»), внизу «или с сервера панели: kerberos ssh <нода>» — только если есть ключ администратора. Ниже прокручиваемые блоки (K23): «✗ Не применилось» — изменение и причина под ним; «✓ Что сделал KERBEROS» — строка на область с мерами и нодами (у «Своего домена» — домены), пробел открывает изменения области по нодам: сайт-заглушка, продления на nginx, копии хостов, отпечатки ключей хоста; «✎ Осталось вам» — как блок «Сделать вам» на S6. Закреплённый низ — блок «Дальше»: «Через сутки уберите старые имена командой:» и команда (или «автоматически» — только если таймер финализации поставлен), «Откатить командой:» и сама команда отдельной строкой без переноса, путь к `report.md`. В терминале ниже 38 строк закреплённые блоки теряют рамки, а большие цифры оценки — строку. Клавиша `s` показывает отчёт целиком простым текстом с прокруткой.

## 7. Доступ к панели Remnawave

### 7.1 Поиск на сервере
1. `docker ps` и `docker inspect`: контейнер с образом `remnawave/backend`. Из него: опубликованный порт API (обычно `127.0.0.1:3000`), тег образа, версия из `/opt/app/package.json` в контейнере.
2. Если контейнера нет: S2 спрашивает адрес API.
3. Из `.env` панели (путь из метки compose контейнера) KERBEROS читает только ключи `APP_PORT` и `PANEL_DOMAIN`. Остальные значения файла не читаются: там секреты.

### 7.2 Запросы
- База `http://127.0.0.1:<port>/api`. Каждый запрос несёт `x-forwarded-proto: https`, `x-forwarded-for: 127.0.0.1`, `x-real-ip: 127.0.0.1`: без них панель отвечает ошибкой (проверено на живой панели).
- Ответы в обёртке `{response: ...}`; лишние поля игнорируются.
- Таймаут 15 с; 5xx и таймаут повторяются через 1, 4 и 15 с. POST без ответа не повторяется: хост мог создаться.
- Ответ 204 без тела — успех: так 3.4.11 отвечает на `bulk/enable`, `bulk/disable` и `DELETE`.

### 7.3 Вход
Remnawave с 2.x принимает токен входа администратора (`POST /api/auth/login`) только от своего веб-интерфейса: без заголовка `X-Remnawave-Client-Type: browser` на любой запрос отвечает 403 «For API requests you must create own API-token in the admin dashboard». Притворяться браузером KERBEROS не стал (решение владельца, v19): он входит по API-токену, как панель велит программам.
1. `GET /api/auth/status` (без токена): панель отвечает; содержимое ответа не нужно.
2. Сохранённый токен `/var/lib/kerberos/panel.token` (0600, JSON `{token, write}`) проверяется запросом `GET /api/nodes`. Подошёл — S2 ничего не спрашивает. 401 или 403 — S2 говорит, что сохранённый токен больше не подходит, и просит новый. `write` ставится, когда токен введён под объяснением для «Исправления» или когда панель приняла с ним изменение. Запуск, который меняет панель («Исправление», откат, финализация в терминале, клавиша `f` на S6), с токеном без `write` сначала спрашивает: оставить сохранённый токен (у него «Полный доступ» или права на запись) или ввести другой.
3. S2 просит API-токен (поле скрыто) и объясняет, где его создать: «Настройки Remnawave → API токены → +» (кнопка «Создать API токен», так пункты называет русский интерфейс панели); панель показывает токен один раз. Права: «Полный доступ» или список, который можно вставить в окне создания токена: для «Проверки» чтение разделов `nodes`, `hosts`, `config-profiles`, `subscription-template`, `internal-squads`, `subscription-settings`, для «Исправления» ещё запись тех же разделов, кроме `nodes`, и у нод право `nodes:update`: свой домен включает на ноде новый инбаунд Hysteria2 (§10.4). Токен, прошедший `GET /api/nodes`, записывается в `panel.token`; токен не из латиницы, цифр и `._~+/=-` отвергается до отправки, а повтор после сбоя связи шлёт тот же токен (панель показывает новый токен один раз). Если панель в «Исправлении», откате или финализации отказала токену (403), KERBEROS забывает сохранённый токен: следующий запуск попросит новый, а не будет снова упираться в тот же отказ. Root сервера панели и так управляет панелью (её секреты лежат в `.env`), поэтому файл не добавляет риска.
4. Таймер финализации (§10.4) работает по `panel.token`; отдельного токена KERBEROS не создаёт: `/api/tokens` принимает только токен входа администратора. Запуски 3x-ui таймер пропускает (код 3): их финализирует `kerberos finalize` в терминале. Если таймер поставить не удалось (`systemd-run` не сработал), `run.finalizeTimer` — `null`. Таймер без терминала берёт `lock` (§5.4) и ждёт запуск в терминале до 600 с, иначе выходит с кодом 2; без `panel.token` или при отказе панели выходит с кодом 3, и S1 напоминает о финализации.

### 7.4 Эндпоинты

Сверено с исходниками backend 2.8.1 и 3.4.11 (`libs/contract`: контракт 2.8.35 и 3.4.17); заголовки §7.2 проверены на живой панели 2.8.1. Каждый эндпоинт проверяет права API-токена: раздел (`hosts`, `nodes` и другие) и вид, чтение или запись. Лишние поля запроса панель молча отбрасывает, поэтому опечатка в имени поля ошибки не даёт; фейк панели в тестах такие поля отвергает.

| Метод | Путь | Зачем |
|---|---|---|
| GET | `/api/auth/status` | панель отвечает |
| GET | `/api/nodes` | `uuid, name, address, port, isConnected, isDisabled, countryCode, usersOnline` |
| GET | `/api/config-profiles` | профили, инбаунды, какие ноды используют профиль |
| PATCH | `/api/config-profiles` | `{uuid, config}`: self-steal, XHTTP-паддинг на сервере |
| POST | `/api/config-profiles` | `{name, config}`: свой профиль ноды (§10.4); имя 2–30 символов `^[A-Za-z0-9_\s-]+$`, уникальное, `Default-Profile` занято; 409 A114 — имя есть, 409 A113 — тег инбаунда есть в другом профиле |
| DELETE | `/api/config-profiles/{uuid}` | откат своего профиля; панель останавливает все ноды профиля, хосты на нём теряют профиль, но не удаляются; 2.8.1 отвечает 200 `{isDeleted}`, 3.4.11 — 204 |
| GET | `/api/hosts` | хосты с полями для копии |

| PATCH | `/api/nodes` | `{uuid, configProfile: {activeConfigProfileUuid, activeInbounds}}`: инбаунды, которые запускает нода (self-steal, §10.4); панель заменяет список целиком, все инбаунды должны быть из профиля, нода перезапускается; право `nodes:update` |

Форма полей хоста зависит от версии панели: 2.8.x и 3.x используют `tags` и `xhttpExtraParams`, 2.2–2.7 — `tag` и `xHttpExtraParams`. KERBEROS определяет форму по ответу `GET /api/hosts` и пишет в той же; если хосты в этом процессе ещё не читались (откат), клиент сначала читает их. Контрактные тесты покрывают обе формы. SNI очищается пустой строкой: null принимают не все сборки. Пределы полей: `remark` до 40 символов в 2.8.1 (до 100 в 3.4.11), тег `^[A-Z0-9_:]+$` до 36 символов (в 2.2–2.7 единственный тег до 32), не больше 10 тегов, имя шаблона `^[A-Za-z0-9_\s-]+$`. Тег инбаунда уникален на всю панель, а не в профиле (`@@unique([tag])` в 2.8.1 и 3.4.11): профиль с тегом, который есть в другом профиле, панель не создаёт и не сохраняет (409 A113).

### 7.5 Ошибки
401 → «Токен не подходит». 403 → «У токена нет прав на {чтение|запись}: {раздел}» и что сделать: создать токен с этими правами (§7.3). 5xx и таймаут после повторов → экран ошибки с кодом и предложением повторить. Ответ не по схеме → `bad_response`, запуск останавливается до изменений.

### 7.6 3x-ui

Решение владельца (K11): KERBEROS работает и с панелью 3x-ui (MHSanaei/3x-ui). Контракт сверен с исходниками от v2.4 до v3.11.

- **Что защищается.** Сервер, на котором запущен KERBEROS: панель 3x-ui и её Xray на нём же. Для нескольких серверов 3x-ui KERBEROS ставится на каждый. Инбаунды других нод мультинодовой панели v3 (`nodeId` не пуст) KERBEROS не трогает.
- **Поиск.** SQLite `${XUI_DB_FOLDER:-/etc/x-ui}/x-ui.db` (только чтение), таблица `settings`; читаются только ключи `webListen, webPort, webBasePath, webCertFile, webDomain, subEnable, subListen, subPort, subPath, twoFactorEnable`. `XUI_DB_FOLDER` и `XUI_PORT` (v3.4+) берутся из `/etc/default/x-ui`. Логин, пароль, `secret`, токены, `install-result.env` и `x-ui setting -show` (до v2.6 печатает пароль) не читаются. Версия: `/usr/local/x-ui/x-ui -v`. Нет базы (PostgreSQL с v3.1 или нет модуля sqlite3): S2 спрашивает адрес панели.
- **Адрес.** `http(s)://127.0.0.1:<webPort><webBasePath>`; https, если задан `webCertFile`, сертификат на петле не проверяется. Если задан `webDomain`, заголовок Host равен ему (иначе 403). Секретный путь — почти пароль: на экраны, в отчёт и `run.json` он не попадает; ошибки называют только `scheme://host:port`.
- **Вход.** `GET <base>csrf-token` (v3.0+, у старых 404) → токен для заголовка `X-CSRF-Token` каждого POST; `POST <base>login` JSON `{username, password, twoFactorCode}`; сессия — кука в памяти процесса; после входа токен CSRF берётся заново. Ответы — `{success, msg, obj}`, `success: false` при HTTP 200 — ошибка. С заголовком `X-Requested-With: XMLHttpRequest` API без сессии отвечает 401. Пять неудачных входов за 5 минут закрывают вход на 15 минут: S2 предупреждает.
- **Инбаунды.** `GET <base>panel/api/inbounds/list`, `GET .../get/{id}`, `POST .../update/{id}` (тело — инбаунд целиком, как только что прочитан; `settings`, `streamSettings`, `sniffing` отправляются JSON-строками: так принимают все версии), `POST .../onlines` — число онлайн-клиентов. Изменения Xray применяет сам (gRPC с v2.4, при сбое — перезапуск в течение 30 с).
- **Модель.** Нода одна (`uuid: local`, адрес — публичный IPv4 сервера: с интерфейса, иначе по домену панели, иначе вводится в S2), профиль — инбаунды сервера, «хост» — каждый инбаунд (ссылки клиентов 3x-ui строит из инбаунда). Порты включённых инбаундов, панели и подписки не лишние для `ports.public`.
- **Проверки.** Только для Remnawave: `profile.template`, `node.no_profile`, `hy2.foreign_masquerade`, `cdn.origin_direct`, `panel.public`, `panel_server.ssh` (на 3x-ui это `ssh.password` с исправлением), `client.ping_type`, `xhttp.padding`, `xhttp.uplink_get`, `xhttp.post_size`, `host.fingerprint`, `sub.ru_direct`, `sub.probe_interval`, `exit.ru_traffic`, `reserve.missing`, `reserve.same_asn`. Только для 3x-ui: `xui.panel_exposed`, `xui.panel_tls`, `xui.panel_2fa` (§10.2).
- **Доступ (S4).** Без пароля и без вопроса о ключе хоста: KERBEROS root на этом сервере. Скрипт bootstrap §8.2 запускается локально (`python3 -`) с `SSH_CONNECTION` от 127.0.0.1, строка ключа — `from="127.0.0.1",command=...,restrict`, ключ хоста закрепляется из `/etc/ssh/ssh_host_ed25519_key.pub`, порт — из `sshd -T`. Агент вызывается по SSH на 127.0.0.1 (`nodes.json`: `sshAddress`), поэтому изменения доступа подтверждаются новым соединением, как на нодах. Вопроса про ключ администратора нет: ключи человека уже на этом сервере; без них `ssh.key_only` не применяется (`no_admin_key`).
- **Новый порт SSH.** После того как sshd слушает оба порта, S8 просит войти со своего компьютера `ssh -p <port> root@<ip>`: Enter — вошёл, Esc — нет; без ответа таймер агента вернёт всё через три минуты. «Не вышло» откатывает изменение через старый порт (`port_closed`).
- **Self-steal.** Сайт и сертификат — как §10.4 шаг 1; сертификат панели на IP, который установщик 3x-ui выпускает через acme.sh, с этого шага продлевается через nginx (§10.4, K16). Затем изменение `xui.reality`: у включённых Reality-инбаундов сервера `target` (до v2.8 `dest`, слово инбаунда сохраняется) = `127.0.0.1:8445`, домен первым в `serverNames`, старые имена остаются; ключ, shortId и клиенты не меняются. Снимки до и после — в `runs/<runId>/panel/` (0600, в них ключ Reality). Проверка §10.4 шаг 5 без списка нод панели. Финализация через сутки — `kerberos finalize`: в `serverNames` остаётся только домен; таймера нет (3x-ui не даёт KERBEROS токен для него). До финализации 3x-ui кладёт в новые ссылки случайное имя из `serverNames`: часть клиентов получает старое и после финализации обновляет подписку. Откат возвращает Reality из снимка; если её правили руками, показывает различия и спрашивает.

## 8. Доступ к нодам

### 8.1 Транспорт
- `ssh -F /dev/null -i /var/lib/kerberos/id_ed25519 -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=/var/lib/kerberos/known_hosts -o ConnectTimeout=15 -p <port> root@<addr> <command>`.
- Один `ControlMaster` на ноду на время запуска (сокет в `/run/kerberos/`), закрывается в конце.
- Таймаут команды агента 120 с. У `apply`, `confirm`, `rollback`, `undo` и `update` 1200 с: изменение может ставить пакеты (агент ограничивает установку 600 с) и ждать блокировку (§9.3).
- Смена ключа хоста останавливает все команды к ноде, пока человек не подтвердит новый ключ: «Ключ сервера {node} изменился. Так бывает после переустановки сервера, но так же выглядит перехват соединения. Подтверждайте, только если переустанавливали сервер или меняли ключи.» S4 показывает прежний и новый отпечатки; по умолчанию выбран пропуск ноды.

### 8.2 Первичный доступ (bootstrap)
1. **Адрес.** Из `nodes.address` панели; домен резолвится в IPv4 через `Prober` при каждом запуске, адрес для SSH хранится в `nodes.json` (`sshAddress`). Порт SSH по умолчанию 22, другой вводится в S4.
2. **Ключ хоста.** `ssh-keyscan -t ed25519`, отпечаток показывается в S4 и закрепляется после подтверждения.
3. **Вход.** Сначала ключами root сервера панели и ключом агента `ssh -A`, если он проброшен (`BatchMode`, без `IdentitiesOnly`): так человек, у которого ноды пускают только его ключ, входит на них один раз своим ключом, не копируя его на сервер панели. Если нода в ответе на вход ключом не предлагает `password` или `keyboard-interactive`, пароль не спрашивается: он не подойдёт. Иначе KERBEROS приостанавливает экран и запускает `ssh` с терминалом; человек вводит пароль ноды в этом же окне. KERBEROS пароль не читает и не хранит. Вход открывает мастер-соединение (`ssh -M`), и все шаги bootstrap идут по нему: пароль вводится один раз.
4. **Установка.** В этой одной сессии выполняется bootstrap: создать `/var/lib/kerberos` (0700); записать агента в `/usr/local/sbin/kerberos-agent` (0755) и сверить sha256; узнать, с какого адреса нода видит сервер панели (`SSH_CONNECTION`); дописать в `/root/.ssh/authorized_keys` строку, если её ещё нет (строка ключа KERBEROS с другим адресом панели заменяется):
   ```
   from="<panel ip>",command="/usr/local/sbin/kerberos-agent",restrict ssh-ed25519 AAAA... kerberos@<panel hostname>
   ```
5. **Проверка.** Новое соединение ключом KERBEROS, команда `version`. Не прошло: доступ считается не установленным, строка ключа убирается тем же bootstrap-соединением.
6. На ноде без `python3` bootstrap предлагает поставить `python3-minimal` (с подтверждением).

### 8.3 Обновление агента
Команда `update <sha256>` с новым файлом в stdin. Версия агента сверяется в начале каждого запуска.

### 8.4 Ограничения ключа
Ключ KERBEROS принимается только с IP сервера панели и запускает только агента, shell на нодах он не даёт. Но среди команд агента есть установка ключа администратора без ограничений (`access.admin_keys`) и обновление самого агента (`update`): захват сервера панели фактически даёт root на нодах. Сервер панели нужно защищать не хуже нод. Если исходящий IP сервера панели сменится, KERBEROS не сможет войти; S4 предложит переустановить доступ.

### 8.5 Ключ администратора
Вход по паролю выключается, только если у человека остаётся свой вход по ключу (§10.3, `ssh.key_only`). В «Исправлении» S4 предлагает при каждом входе на экран, с прежним ответом по умолчанию (в «Проверке» вопроса нет: она не меняет настроек серверов; клавиша `f` на S6 задаёт его перед переходом в «Исправление»); выбранные ключи попадают на ноды изменением после экрана согласия:
1. **Ключи, которыми человек входит на сервер панели** (`/root/.ssh/authorized_keys` сервера панели): список с комментариями и отпечатками, отмеченные копируются на выбранные ноды. Так человек сохраняет вход со своего компьютера тем же ключом.
2. **Ключ на сервере панели**, если своих ключей нет: KERBEROS создаёт `admin_ed25519` и ставит его на ноды без ограничений. Вход на ноду: `kerberos ssh <нода>` с сервера панели.
3. **Пропустить:** тогда `ssh.key_only` на этих нодах не применяется (код `no_admin_key`), отчёт объясняет почему.

Ключи из пунктов 1 и 2 ставит исправление `access.admin_keys` (`{keys}`, бэкап `authorized_keys`, откат): в плане оно стоит перед `ssh.key_only` и отмечается вместе с ним.

## 9. Агент

Один файл `kerberos/agent.py`, Python 3.9+, только стандартная библиотека; протокол 1. На ноде: `/usr/local/sbin/kerberos-agent`, состояние и бэкапы в `/var/lib/kerberos/`.

### 9.1 Команды
Агент читает `SSH_ORIGINAL_COMMAND`, принимает только команды из таблицы, параметры сверяет регулярным выражением, данные получает JSON-ом в stdin. Отвечает одним JSON-объектом в stdout; при ошибке код возврата не 0 и тело `{"error": {"code": "...", "message": "..."}}`.

| Команда | stdin | Ответ |
|---|---|---|
| `version` | нет | `{protocol: 1, agent, sha256}`: `sha256` файла агента на ноде |
| `facts` | нет | `AgentFacts` |
| `watch` | нет | `AgentWatch` |
| `site-check` | `{domain}` | `{template, altSvc, status}`: структура заглушки для `site.same_template` |
| `edge-sources` | `{path}` | `{nets: {net, count}[]}`: источники запросов к пути туннеля в логах nginx, /24, без адресов клиентов |
| `plan <fixId>` | параметры | `{files: {path, content}[], commands: string[], packages: string[]}`; у файлов, собранных из файлов человека (`docker-compose.yml`, сайт nginx, `10-kerberos.conf`, `authorized_keys`), `content` равен `null`: в них бывают секреты (§9.4) |
| `apply <fixId> <changeId>` | параметры | `AgentChange` |
| `confirm <changeId>` | нет | `AgentChange` |
| `rollback <changeId>` | нет | `AgentChange` |
| `undo <changeId>` | нет | `AgentChange`: только для таймера §9.3. Изменение, которое ещё ждёт подтверждения, откатывается; откат порта SSH, который ждёт подтверждения (`rollback_pending`), возвращается к подтверждённому состоянию; иначе `noop` |
| `update <sha256>` | новый файл агента | `{agent}` |

### 9.2 Контракты ответов

```python
class AgentFacts(TypedDict):
    protocol: Literal[1]
    agent: str                         # semver
    os: dict                           # {id, version, kernel}
    ipv4: list[str]                    # global unicast only
    ipv6: list[str]
    python: str
    listening: list[dict]              # {proto, address, port, process, docker, firewalled}
    ssh: dict                          # {ports, socketActivated, passwordAuthentication,
                                       #  kbdInteractive, permitRootLogin, adminKeys}
                                       # ports: port and listenaddress of sshd -T, else sshd in ss;
                                       # adminKeys: lines without command= and restrict, not KERBEROS
    fail2ban: dict                     # {installed, sshdJail, jailPorts}
    mptcp: dict                        # {enabled, ipOptionsDrop, sockets}
    nodeApi: dict                      # {port, panelOnly, otherPeers, panelPeer}; panelPeer: an
                                       # established connection to port from the KERBEROS address
    nftTables: list[str]
    hostKeys: list[dict]               # {type, fingerprint} as ssh-keygen -l, hostkey files of sshd -T
    firewall: dict                     # {ufw: 'active' | 'inactive' | 'absent'}
    remnanode: dict                    # {present, network: 'host' | 'bridge' | None, xrayVersion,
                                       #  nodePort, letsencryptMounted}
    nginx: dict                        # {installed, realip, sites: [{file, serverNames, listen}]}
    certbot: dict                      # {installed, certs: [{domain, notAfter}], stopsNginx}; stopsNginx:
                                       # a pre-hook certbot runs before every renewal stops nginx (§10.4)
    acme: list[dict]                   # {tool: 'acme.sh' | 'certbot', name, names, notAfter, freesPort, blocked?}:
                                       # renewals that open :80 themselves (§10.4); freesPort: a pre-hook of it stops
                                       # or kills something first; blocked: why KERBEROS cannot move one
    watch: dict                        # {installed}

class FamilyWatch(TypedDict):
    connections: int
    clientIps: int                     # count only, never the addresses
    cut: int                           # <= 1500 bytes received, silent > 3 s
    cutNets: list[dict]                # {net, count}; /16 for IPv4, /32 for IPv6

class AgentWatch(TypedDict):
    protocol: Literal[1]
    at: str
    port: int | None                   # TCP port Xray (xray*, rw-core) answers on beyond loopback, 443
                                       # first; None: no such port, the counters stay zero (K18)
    ports: list[int]                   # every such port; the counters cover all of them
    v4: FamilyWatch
    v6: FamilyWatch
    xray: dict                         # {accepted5m, users5m, ruShare} from the xray log tail, counts only

class AgentChange(TypedDict):
    protocol: Literal[1]
    changeId: str                      # uuid4
    fixId: str
    state: Literal['applied', 'pending_confirm', 'confirmed', 'rollback_pending', 'rolled_back',
                   'noop', 'failed']
    files: list[str]
    details: dict                      # e.g. new ssh port, host key fingerprints
```

Коды ошибок агента: `bad_params`, `unknown_command`, `sha_mismatch`, `no_admin_key`, `sshd_test_failed`, `ssh_port`, `port_busy`, `bridge_network`, `docker_published`, `mptcp_absent`, `port80_busy`, `certbot_failed`, `nginx_test_failed`, `realip_enabled`, `apt_failed`, `change_conflict`, `no_backup`, `backup_damaged`, `not_implemented`, `command_failed`, `panel_not_peer`, `acme_check_failed`, `acme_standalone`, `certbot_hook`.

### 9.3 Изменения и откат на ноде
- Повторный `apply` с тем же `changeId` ничего не делает и возвращает прошлый результат (`noop`).
- Перед изменением агент копирует затрагиваемые файлы в `/var/lib/kerberos/changes/<changeId>/` и пишет `rollback.json`: прежние байты, права, существовал ли файл, команды отката.
- Изменения доступа (`ssh.key_only`, `ssh.port`, `hostkeys.regenerate`) ставят таймер `systemd-run --on-active=180 --unit kerberos-undo-<changeId> /usr/local/sbin/kerberos-agent undo <changeId>` и состояние `pending_confirm`. KERBEROS открывает новое соединение и вызывает `confirm`; таймер снимается. Не дошёл `confirm`: агент сам откатывает изменение через три минуты.
- `rollback` возвращает файлы до прежних байтов и прав и выполняет команды отката. Агент хранит sha256 записанных файлов; если файл изменился позже (например, его тронуло более позднее изменение), откат отказывает с `change_conflict`: сначала откатывается более позднее изменение.
- Изменение, ждущее подтверждения, записано в `/var/lib/kerberos/pending`; новый `apply` при нём отказывает с `change_conflict`.
- `apply`, `confirm`, `rollback`, `undo` и `update` идут по одной: блокировка `/var/lib/kerberos/agent.lock` (`flock`), ожидание до 150 с, иначе `change_conflict`. Таймер и `confirm` по SSH поэтому не встречаются на середине изменения.
- Перезапуск `ssh.socket` всегда идёт после `systemctl reset-failed ssh.socket ssh.service`: иначе после нескольких перезапусков подряд systemd выключает сокет (`start-limit-hit`). Перед `sshd -t` агент создаёт `/run/sshd`, если его нет.
- Откат подтверждённого `ssh.port` идёт в две фазы, как применение: доступ по SSH меняется только с таймером и подтверждением новым соединением. `rollback` возвращает раскладку первой фазы (слушают старый и новый порты), ставит тот же таймер и отвечает `rollback_pending` (`details.oldPorts`, `newPort`). KERBEROS входит на старый порт новым соединением и вызывает `confirm`: агент возвращает исходные файлы, снимает таймер и отвечает `rolled_back`. Без `confirm` таймер (`undo`) возвращает подтверждённую раскладку, только новый порт. Пока откат ждёт подтверждения, `apply` отказывает с `change_conflict`. Откат `ssh.key_only` и `hostkeys.regenerate` однофазный: доступа он не отнимает.
- `rollback` изменения `access.admin_keys` отказывает с `change_conflict`, пока действует более позднее `ssh.key_only`: иначе вход по паролю выключен, а ключа нет. Порядок изменений агент хранит в их записях (`order`).
- Команда отката не выполнилась: агент всё равно возвращает файлы, пишет `rolled_back` с `details.undoProblems` и отвечает `command_failed` со списком команд. При сбое `confirm` таймер снимается только после удачного возврата файлов.
- Подтверждение, пережившее таймер (перезагрузка, сбой `undo`): если изменение ждёт дольше 180 + 60 с, а таймер `kerberos-undo-<changeId>` не ждёт и не работает, следующий `apply` сначала откатывает его, как сделал бы таймер.
- Откат возвращает службы как были: юнит, который был до изменения (исправление применяли повторно), снова включается или выключается, запускается или останавливается, а не выключается всегда; fail2ban и nginx, выключенные человеком, после отката снова выключены.

### 9.4 Приватность
Агент не пишет и не отдаёт адреса клиентов, email и UUID пользователей, ключи Reality и `SECRET_KEY` ноды. Наружу уходят счётчики и сети /16.

## 10. Проверки и исправления

### 10.1 Правила
- Проверка смотрит на действующее состояние, а не на имена файлов: `sshd -T`, правила nft, `sysctl`, ответ снаружи. Мера, поставленная вручную или другим скриптом, считается выполненной, и KERBEROS её не дублирует.
- Исправление KERBEROS применяется, только если проверка нашла проблему и все условия исправления выполнены. Иначе в отчёте причина.
- Каждое исправление: план (что изменится) → бэкап → применение → перепроверка находки. Перепроверка не прошла: изменение откатывается, отчёт показывает «не применено» и причину.
- Исправления на одной ноде идут по одному, ноды по очереди. Порядок на ноде: `access.admin_keys`, `mptcp.guard`, `fail2ban.sshd`, `node_api.panel_only`, `ports.drop`, `hostkeys.regenerate`, `ssh.key_only`, `ssh.port`, `node.letsencrypt_mount`, `self_steal`, `cdn.edge_only`, `watch.install`; затем исправления в панели, последними `panel.portal` и `xui.panel_hide` (§10.10).

### 10.2 Каталог по темам

Столбец «Действие»: идентификатор исправления KERBEROS, «вручную» (отчёт объясняет, что сделать) или «объяснение» (мера сознательно не применяется).

**Тема 1. Хостинг и AS**

Находка только там, где так | вручную: перевести продление на webroot той программы или остановку её хуком; «Свой домен» переводит такие продления на nginx сам (§10.4) **[новое]** |
| `acme.stop_hook` | средний | общий хук certbot (`/etc/letsencrypt/renewal-hooks/pre/`, `pre-hook` в `cli.ini`) останавливает nginx перед каждым продлением (`certbot.stopsNginx`), а на ноде сайт «Своего домена»: его сертификат продлевается через nginx и не продлится. Находка только у нод с сайтом KERBEROS и таким хуком | вручную: остановку nginx перенести в `pre_hook` и `post_hook` тех сертификатов, которым она нужна **[новое]** |

**Тема 3. Защита от сканирования РКН**

| checkId | Риск | Что проверяем | Действие |
|---|---|---|---|
| `ssh.password` | высокий | `passwordauthentication yes`, `kbdinteractiveauthentication yes` или `permitrootlogin yes` | `ssh.key_only` **[парк]** |

### 10.3 Исправления на ноде

Файлы и команды ниже повторяют меры, стоящие на парке. Агент пишет их через бэкап §9.3.

**`ssh.key_only`.** Условие: на ноде есть ключ администратора кроме ключа KERBEROS (§8.5; строки с `command=` или `restrict` не считаются: по ним не войти), иначе `no_admin_key`. Файл `/etc/ssh/sshd_config.d/10-kerberos.conf` (имя с `10-`, чтобы читаться раньше `50-cloud-init.conf`):
```
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin prohibit-password
```
`sshd -t` (не прошёл: файл удаляется, `sshd_test_failed`), `systemctl reload ssh`, таймер отката, `confirm` после нового входа. Перепроверка: `sshd -T` и снаружи сервер предлагает только `publickey`.

**`ssh.port`.** Новый порт выбирается случайно из 20000–32767 (ниже эфемерного диапазона), свободный по `facts.listening`. Две фазы:
1. `apply`: sshd слушает старый и новый порт. При `ssh.socket` (`facts.ssh.socketActivated`, по умолчанию Ubuntu 24.04 и 26.04) порт задаёт drop-in `/etc/systemd/system/ssh.socket.d/zz-kerberos.conf` (`ListenStream=` сбрасывает список, дальше все текущие адреса с обоими портами), иначе строки `Port` в `10-kerberos.conf`. Если ufw активен: `ufw allow <port>/tcp`. Джейл fail2ban получает оба порта. Таймер отката.
2. KERBEROS входит на новый порт новым соединением и вызывает `confirm`: агент убирает старый порт (в режиме `sshd_config` и строки `Port` основного файла), обновляет джейл, снимает таймер; `nodes.json` получает новый порт. Файлы второй фазы агент бэкапит ещё в `apply`, поэтому откат возвращает всё к исходному.
Перепроверка не прошла после подтверждения: откат идёт в две фазы (§9.3) и подтверждается входом на старый порт; удался — `nodes.json` снова со старым портом. Отчёт выделяет новый порт крупно. Если порт закрыт фаерволом хостера, новое соединение не проходит, таймер возвращает всё через три минуты, отчёт говорит открыть порт в панели хостера.

**`fail2ban.sshd`.** Пакеты `fail2ban python3-systemd`; `/etc/fail2ban/jail.d/zz-kerberos.local`:
```ini
[DEFAULT]
ignoreip = <действующий ignoreip человека> 127.0.0.1/8 ::1 <panel ip>
[sshd]
enabled = true
port = <ssh ports>
backend = systemd
maxretry = 5
findtime = 10m
bantime = 1h
```
Список `ignoreip` человека (из `jail.local` и других файлов `jail.d`, в том числе у `[sshd]`) сохраняется: наш файл читается последним и иначе заменил бы его. HTTP-джейлы не включаются: они банили бы edge-серверы CDN.

**`mptcp.guard`.** `/etc/sysctl.d/98-kerberos-mptcp.conf` с `net.mptcp.enabled = 0`; таблица nft `inet kerberos_mptcp` (`ip protocol tcp ip hdrlength > 5 counter drop`), загружается юнитом `kerberos-mptcp.service` (oneshot, `RemainAfterExit`). Не через `/etc/nftables.conf`: его `flush ruleset` снёс бы правила Docker. Перезапуск Xray не нужен. Число MPTCP-сокетов агент берёт из `/proc/net/protocols`, а не из `ss -M`: iproute2 6.1 в этом режиме выводит и TCP.

**`node_api.panel_only`.** Таблица nft `inet kerberos_node_api`, input priority -10: `tcp dport <nodePort> ip saddr <panel ip> accept`, затем `tcp dport <nodePort> drop` (отбрасывает и IPv6); юнит `kerberos-node-api.service`. IP панели: тот, с которого нода видит KERBEROS (§8.2), он же сверяется с пирами на `nodePort` (`facts.nodeApi`): если с этого адреса нет установленного соединения (`panelPeer` false: панель ходит к ноде по IPv6 или через NAT), строка плана заблокирована, а агент отказывает (`panel_not_peer`). При `remnanode.network = bridge` агент отказывает (`bridge_network`). Перепроверка: счётчик accept растёт, статус ноды в панели и время его изменения не меняются; KERBEROS смотрит `isConnected` ноды в панели 30 с (6 раз по 5 с), упала связь — изменение откатывается.

**`hostkeys.regenerate`.** Бэкап ключей хоста: файлов из строк `hostkey` в `sshd -T` (по умолчанию `/etc/ssh/ssh_host_*`), их же читает `facts.hostKeys`. Новые ключи тех же типов по тем же путям по одному (`ssh-keygen -q -t <тип> -N '' -f <путь>`, ECDSA того же размера, ed25519 всегда; не `ssh-keygen -A`: до OpenSSH 9 он создаёт и DSA-ключ, которого откат не уберёт; уже лежащий DSA-ключ не трогается), `sshd -t`, `systemctl reload ssh`, таймер отката. KERBEROS читает новый отпечаток в ответе агента, сверяет его с `ssh-keyscan`, обновляет `known_hosts` и вызывает `confirm`; если сервер показывает не новый ключ, `confirm` не вызывается, изменение откатывается с `hostkey_mismatch`. Перепроверка не прошла после подтверждения: откат возвращает и прежний ключ в `known_hosts`. Отчёт перечисляет новые отпечатки: людям с этим сервером в `known_hosts` нужно `ssh-keygen -R <ip>`.

**`ports.drop`.** Правило nft `iifname != "lo" tcp dport <port> drop` для каждого порта в таблице `inet kerberos_ports`. Порт, опубликованный Docker, не трогается (`docker_published`). Порт SSH не закрывается никогда: для порта текущего соединения (`SSH_CONNECTION`), портов sshd и `ssh.socket` агент отказывает (`ssh_port`).

Если на ноде нет `nft` (облачные образы Debian), исправление ставит пакет `nftables`; откат его не удаляет. Таблицы nft всех исправлений лежат в `/etc/kerberos/<name>.nft` (загрузка идемпотентна: `table`, `flush table`, правила) и грузятся юнитами `kerberos-<name>.service` (oneshot, `RemainAfterExit`, `ExecStop` удаляет таблицу). Если юнит был до изменения, откат возвращает файлы и перезапускает его, а не выключает (§9.3).

**`watch.install`.** `/usr/local/sbin/kerberos-watch` и `/etc/cron.d/kerberos-watch` (каждые 5 минут), лог `/var/log/kerberos-watch.log`, logrotate раз в месяц. Строка: время, порты Xray, соединения, число клиентских IP, срезанные соединения с сетями /16, пользователи и запросы Xray за 5 минут. Адресов и идентификаторов нет. Один запуск 0,1–0,35 с. Пакеты `cron` и `logrotate` ставятся, если их нет (в минимальных образах Debian нет cron). Скрипт считает кодом агента (`collect_watch`), чтобы на ноде был один файл с логикой. Откат убирает скрипт, cron и logrotate; лог остаётся.

### 10.4 Self-steal: свой домен, копии хостов, старые выключаются

Нода переходит на свой домен: домен, IP и сертификат совпадают, любой, кто зайдёт на IP, видит обычный сайт.

Условия (S7 проверяет и показывает каждое):
- нода подключена к панели. Профиль, общий с другими нодами, исправление не останавливает: нода получает свой профиль («Свой профиль» в шаге 2), как и нода без профиля. Нода, которая на общем профиле запускает и другие инбаунды, кроме Reality и Hysteria2 шаблона (XHTTP за CDN, второй Reality), заблокирована: «на общем профиле нода держит ещё {tags}: их KERBEROS не переносит» (`plan.blocked.shared_other`); перенос с переименованием их тегов, хостов и правил — бэклог;
- если ни один внутренний сквад не держит инбаунды ноды (новая нода): один сквад в панели — он, без вопроса; несколько — строка ждёт клавишу `u`: список сквадов с числом пользователей (`info.membersCount`), отмечены те, где есть инбаунды других нод; без выбора строка не отмечается;
- человек вводит домен ноды прямо в строке плана; A-запись указывает на IPv4 ноды, AAAA, если есть, на её IPv6. Пока DNS не совпадает, S7 показывает нужную запись и раз в 10 секунд проверяет снова;
- общий хук certbot не останавливает nginx (`facts.certbot.stopsNginx`, §10.2 `acme.stop_hook`): сертификат домена KERBEROS выпускает через nginx, и он бы не продлился; строка заблокирована (`plan.blocked.certbot_hook`), агент отказывает (`certbot_hook`);
- 80/tcp на ноде свободен или его держит служба nginx (`nginx.service` активна; контейнер с именем nginx не в счёт); 443/tcp держит Xray: процесс `xray*` (3x-ui запускает `xray-linux-<arch>`) или `rw-core`, а на 3x-ui и порт включённого инбаунда.

Предупреждение до согласия, дословно `fix.self_steal.warning` (§15).

Шаги, каждый пишется в журнал запуска:
1. **Сайт и сертификат** (агент, `self_steal.site {domain, siteSeed}`). nginx, если его нет; на 80/tcp ACME webroot `/var/www/kerberos-acme` и редирект на https; certbot `--webroot --register-unsafely-without-email`; сайт-заглушка на `listen 127.0.0.1:8445 ssl`, сгенерированный из `siteSeed`: вид заведения, название, тексты, цены, цвета, шрифты, иллюстрация и разметка свои у каждой ноды (см. `site.same_template`), без внешних ресурсов; хук продления перезагружает только nginx: Xray сам перечитывает сертификаты раз в час.
   - **Продления на 80-м порту** (K16). После этого шага 80-й порт занят nginx, и сертификаты, которые продлеваются сами через этот порт, больше не продлились бы. Агент находит их (факт `acme`): acme.sh с записью `no` в `Le_Webroot` (`/root/.acme.sh/<имя>[_ecc]/<имя>.conf`) и certbot с `authenticator = standalone` (`/etc/letsencrypt/renewal/*.conf`), если порт продления 80. Продление, перед которым хук останавливает nginx (команда хука с nginx и stop, kill или quit либо `fuser -k 80/tcp`; хуки: у acme.sh `Le_PreHook`, у certbot `pre_hook` записи, исполняемые файлы `/etc/letsencrypt/renewal-hooks/pre/` без `~` в конце и `pre-hook` в `cli.ini`; комментарии не в счёт), получает порт само и не трогается; reload или проверка nginx порт не освобождают. Если хук продления останавливает или убивает что-то другое, в факте `freesPort` true: оно переводится, но `acme.port80` его не трогает (K17).
   - Имена продлений (у acme.sh — домены записи, у certbot — имена из сертификата, IP тоже, IDN в punycode) входят в `server_name` блока :80, а продление переходит на webroot `/var/www/kerberos-acme`: у acme.sh записи `no` в `Le_Webroot` становятся этим путём, у certbot ставятся `authenticator = webroot` и `webroot_path = /var/www/kerberos-acme,`, а записи `[[webroot_map]]`, если они есть, тоже указывают на этот путь (certbot берёт их раньше `webroot_path`). Имена продлений, переведённых раньше, остаются в `server_name` и при повторном self-steal.
   - Продление, которое KERBEROS перевести не может, — `blocked` в факте: у certbot метод задан в `/etc/letsencrypt/cli.ini` (`authenticator`, `standalone`, `webroot`, `webroot-path`: они главнее файла продления), или имя nginx не примет (не домен и не IP, IPv6 с зоной). Тогда строка self-steal в S7 заблокирована (`plan.blocked.acme_standalone`), а агент отказывает (`acme_standalone`): после self-steal такой сертификат перестал бы продлеваться.
   - Перед переводом агент кладёт в webroot пробный файл и запрашивает его у nginx на 80-м порту публичного IPv4 ноды (если его нет на интерфейсах — `127.0.0.1`) с Host каждого имени: nginx выбирает сервер сначала по адресу, как для центра сертификации. Не отдан — `acme_check_failed`, ничего не переведено, изменение откатывается. Снаружи эти продления и раньше приходили на 80-й порт ноды, меняется только, кто отвечает: nginx вместо их собственного слушателя. Пробный файл удаляется; он записан в изменение как файл, которого не было, поэтому оборванное применение и его откат тоже его убирают.
   - Откат возвращает только способ продления: у acme.sh прежние записи `Le_Webroot`, у certbot `authenticator = standalone`, прежние `webroot_path` и записи `webroot_map` (записи на webroot KERBEROS, которые certbot дописал сам после продления, уходят). Файлы целиком не возвращаются: acme.sh и certbot переписывают их при каждом продлении. Если способ продления после KERBEROS поменяли, откат его не трогает.
2. **Профиль по нашему шаблону** (`PATCH /api/config-profiles`, снимок до изменения в `runs/<runId>/panel/`). Профиль ноды собирается из `templates/profile.json` по правилам §10.9: Reality с `dest = "127.0.0.1:8445"` и `serverNames = [<домен>, <старые имена>]`, Hysteria2 с сертификатом домена и masquerade на домен; приватный ключ, shortId и теги существующих инбаундов сохраняются; прочие инбаунды пользователя остаются. Нельзя ставить `dest = <домен>:443`: Reality подключится сам к себе. Сертификат для Hysteria2 контейнер ноды должен видеть в `/etc/letsencrypt`; если тома нет, перед этим шагом идёт `node.letsencrypt_mount` (§10.9). Панель перезапускает Xray на ноде: клиенты переподключаются за секунды. Панель хранит конфиг нормализованным (чистит `clients`, сортирует), поэтому записанным считается профиль из её ответа на `PATCH`: с ним откат и финализация сравнивают профиль в панели. Панель запускает на ноде только инбаунды из её `configProfile.activeInbounds`, а новый инбаунд профиля туда сам не попадает: инбаунды шаблона, которых там нет (обычно Hysteria2), KERBEROS сразу включает на ноде (`PATCH /api/nodes`, изменение `self_steal.node`, право `nodes:update`) и сверяет ответ (`node_mismatch`). Откат убирает из списка ноды только добавленное KERBEROS; ноду, которую перевели на другой профиль, не трогает.
   - **Свой профиль** (K24). Нода на общем профиле или без профиля вместо `PATCH` получает свой профиль: `POST /api/config-profiles` (изменение `self_steal.own_profile`, записанный конфиг — снимок 0600) с именем `KERBEROS <NODE>` (`<NODE>` как в тегах §10.9; имя до 30 символов, при совпадении « 2», « 3»). Конфиг собирается из шаблона, как выше, по Reality и Hysteria2, которые нода запускает на общем профиле: ключ, shortId и старые имена Reality сохраняются (клиенты со старой подпиской сутки входят через новый инбаунд), теги новые: `VLESS-REALITY-<NODE>`, `HY2-<NODE>`, при совпадении с тегом любого профиля панели `-2`, `-3`. У ноды без профиля ключ и shortId новые. Других инбаундов общего профиля в своём нет. Если ответа на `POST` нет, KERBEROS ищет профиль по имени, и найденный удаляет откат. Дальше: новые инбаунды в сквады (ниже), нода на свой профиль — `PATCH /api/nodes` с новым профилем и его инбаундами (`self_steal.node`, `details.beforeProfile` — прежний профиль), копии хостов на новые инбаунды (шаг 3). Общий профиль и другие ноды на нём не меняются; финализация работает со своим профилем.
   - **Сквады** (`self_steal.squads`). Новые инбаунды шаблона идут в те сквады, где были инбаунды ноды до self-steal (на общем профиле — Reality и Hysteria2 этой ноды), а если таких нет — в сквады, выбранные в S7, и тогда все инбаунды шаблона. Сквады меняются до того, как нода запустит новые инбаунды: пользователи уже на месте, когда нода перезапустится. Откат убирает из сквада только добавленное KERBEROS (`details.added`).
3. **Копии хостов.** Для каждого включённого хоста этих инбаундов (только Reality и Hysteria2, которые шаблон собрал в профиль; хосты прочих инбаундов пользователя не копируются и не выключаются, их теги в `details.tags` изменения профиля) `POST /api/hosts` со всеми полями исходного, кроме: `sni = <домен>`, `overrideSniFromAddress = false`, `keepSniBlank = false` (иначе клиенты получат пустой SNI), `fingerprint` = исходный или `firefox`, если пустой; `xrayJsonTemplateUuid` = шаблон KERBEROS с резервом или без (§10.9); `tags` и `isHidden` по выбору резерва. Если у ноды нет хоста для Hysteria2-инбаунда, KERBEROS создаёт его по образцу хоста Reality с портом 443 и тем же адресом; заметка — заметка хоста Reality и « Hysteria2», укороченная до 40 символов (предел 2.8.1). На общем профиле хост — хост ноды, если он привязан к ней (`nodes`), его адрес — адрес ноды или домен, который резолвится в её IPv4; хосты, которые не относятся ни к одной ноде профиля, не трогаются. У своего профиля копия получает `inbound` нового инбаунда того же типа. Если у ноды нет ни одного включённого хоста Reality, KERBEROS создаёт его сам: заметка — флаг страны ноды и её имя («🇳🇱 nl-1», до 40 символов), адрес ноды из панели, порт инбаунда, `sni` — домен, `fingerprint = firefox`, шаблон KERBEROS; по нему создаётся хост Hysteria2, как выше. Каждую копию KERBEROS читает обратно и сверяет поля. Копии встают в конец списка, отчёт об этом пишет; переупорядочивание через API в панели есть, но KERBEROS его пока не использует (§23, Q4; бэклог).
4. **Выключить старые хосты** (`POST /api/hosts/bulk/disable {uuids}`). Не удалять: откат включает их обратно. Список пишется в журнал до запроса: если ответ не пришёл, откат всё равно их включит.
5. **Проверка с сервера панели.** TLS без SNI на `<ipv4>:443` отдаёт сертификат домена; с SNI домена сайт отвечает 200; нода в панели подключена (до шести раз по 5 с: после `node.letsencrypt_mount` панель находит пересозданный контейнер не сразу). Находка `reality.foreign_sni` перепроверяется только для инбаундов, которые изменил этот self-steal (выключенные инбаунды 3x-ui проверки не смотрят). Результаты проб, DNS и факты записываются в данные запуска только после всей проверки: откат не оставляет завышенной оценки.
6. **Через 24 часа: финализация.** Старые имена убираются из `serverNames`. Клиенты, не обновившие подписку за сутки, перестанут подключаться через эту ноду. Финализацию запускает `kerberos finalize`: S1 напоминает о ней при каждом запуске после 24 часов, а опция «Сделать автоматически» в S7 ставит таймер systemd `kerberos-finalize-<runId>.timer` на сервере панели с токеном из §7.3. Экран финализации перечисляет для каждой ноды, какое имя останется и какие уйдут («{node}: останется {domain}, уберётся {old}»); если у части нод не вышло, он называет их, а S1 напомнит о них при следующем запуске.

Ошибки: шаг 1 → откат агента; шаг 2 → профиль из снимка, откат агента (если ответа на `PATCH` нет, записанным считается профиль, который панель держит после него); шаг 3 до выключения старых → удалить созданные копии, профиль из снимка, откат агента; шаг 4 и дальше → полный откат ниже. Если шаг не откатился (профиль правили после KERBEROS, панель отказала), более ранние шаги этого self-steal остаются на месте с `rollback_skipped`: Reality на неоткаченном профиле смотрит на сайт, и убирать его нельзя; всё это доделывает `kerberos rollback`. Шаг панели, оборванный на середине (PATCH без ответа, исключение), откатывается первым, профиль тоже возвращается из снимка; неожиданная ошибка самого KERBEROS даёт `internal_error`.

Свой профиль (K24) откатывается последним из шагов панели: копии удаляются, старые хосты включаются, нода возвращается на прежний профиль с прежними инбаундами (если её не перевели на другой), из сквадов уходит добавленное, затем `DELETE /api/config-profiles/{uuid}` — только если на профиле нет нод и хостов, кроме самой ноды, у которой профиля не было (удаление вернёт её к «без профиля»); иначе профиль остаётся с `profile_in_use`, и отчёт говорит почему. Профиль, который правили после KERBEROS, удаляется после diff и вопроса.

Откат после успеха: профиль из снимка (если в панели правили руками, откат показывает diff и спрашивает); `bulk/enable` старых хостов; удаление копий; откат агента (конфиг nginx возвращается, сертификат остаётся: он ничего не выдаёт; продления, переведённые на nginx, снова продлеваются сами через 80-й порт).

### 10.5 Исправления в панели
- **`sub.template`.** Находки `sub.ru_direct` и `sub.probe_interval` исправляются не правкой шаблонов пользователя, а переводом хостов на шаблоны KERBEROS (§10.9): копии хостов self-steal получают их сразу, остальным включённым хостам с находкой `PATCH /api/hosts {uuid, xrayJsonTemplateUuid}`. Шаблоны пользователя не меняются; откат возвращает хосту прежний шаблон. В шаблонах KERBEROS уже есть `geoip:ru` и `geosite:category-ru` напрямую и проба раз в 60 с (переключение на резерв в среднем около 35 секунд, в худшем около 2 минут).
- **`sub.ping_type`.** В `customResponseHeaders` добавляется `ping-type: proxy-head`: Happ меряет задержку HEAD-запросом через туннель, а не прямым ICMP или TCP на IP ноды. Остальные заголовки сохраняются: PATCH заменяет объект целиком, поэтому чтение и слияние. Поведение Happ и Incy проверяется на устройствах в задаче K7 (§23, Q1).
- **`host.fingerprint`.** `PATCH /api/hosts {uuid, fingerprint: "firefox"}`.
- Хост переводится на «KERBEROS», если у его ноды есть пара с резервом (скрытый хост с тем же тегом на другой ноде), иначе на «KERBEROS single».
- Откат исправлений в панели: прежний объект из снимка; если текущий объект отличается от того, что записал KERBEROS, откат показывает diff и спрашивает. Так же сверяются `reserve`, `sub.template` и `sub.templates`: KERBEROS хранит записанное (`details.written`, у шаблонов ещё снимок `details.writtenPath`, 0600) и пишет его до PATCH. Автоматический откат во время S8 чужие правки не затирает: изменение остаётся на месте с `rollback_failed` (`rollbackError: changed_in_panel`), а спросит `kerberos rollback`.
- Изменение в панели, которое упало на середине (часть объектов уже записана), сразу откатывает записанное и получает состояние `rolled_back` с кодом ошибки панели; исключение не из панели откатывает так же, с `internal_error`.
- Хост с `xrayJsonTemplateUuid = null` пользуется шаблоном XRAY_JSON панели по умолчанию: KERBEROS считает им шаблон с именем `Default` (без учёта регистра), а без такого шаблона хост не проверяет (§23, Q9).

### 10.6 XHTTP и CDN
- **Действующий `extra`.** Клиент получает `xhttpExtraParams` хоста, если он не пуст, иначе `xhttpSettings.extra` инбаунда целиком: панель их не сливает. Проверки `xhttp.padding`, `xhttp.uplink_get` и `xhttp.post_size` смотрят на действующий `extra` хоста.
- **`xhttp.uplink_get`.** Только `extra` хоста: `uplinkHTTPMethod = "GET"`. Хост без своего `extra` получает копию `extra` инбаунда с этим ключом: иначе он потерял бы остальные поля инбаунда. Сервер принимает GET с телом и `seq` как загрузку без изменений инбаунда. Откат: если `extra` хоста после KERBEROS не меняли, возвращается прежний `extra` хоста (в том числе пустой); иначе возвращается только прежнее значение `uplinkHTTPMethod` (или ключ убирается), остальной `extra` остаётся каким есть. Прежний и записанный `extra` лежат в `runs/<runId>/panel/` (0600): в нём бывает паддинг.
- **`xhttp.padding`.** Поля паддинга должны совпадать на сервере и клиенте, иначе туннель рвётся. Исправление пишет один набор в `extra` инбаунда (профиль) и в `extra` каждого его хоста, у которого свой непустой `extra`, одним изменением (хост без своего `extra` получает паддинг вместе с `extra` инбаунда): `xPaddingBytes "100-1000"`, `xPaddingObfsMode true`, `xPaddingKey`, `xPaddingHeader`, `xPaddingPlacement "queryInHeader"`, `xPaddingMethod "tokenish"`; ключ и заголовок случайные на инбаунд, чтобы не было одной сигнатуры на весь парк. Применяется, только если паддинга нет ни у инбаунда, ни у его хостов; частично настроенный паддинг правится вручную. Это исправление в панели для ноды: доступ агента не нужен, в плане оно стоит среди исправлений в панели, одно изменение на ноду. Инбаунд, получивший паддинг за время запуска (профиль общий с другой нодой), пропускается. `xPaddingKey` — 6–10 строчных латинских букв, `xPaddingHeader` — `X-<Слово>-<Xxxx>` (слово из короткого списка вроде `Request`, `Trace`, `Session`). Записанные значения лежат в `runs/<runId>/panel/padding-<changeId>.json` (0600), в `run.json` только путь. Перепроверка: у инбаунда и в действующем `extra` каждого его хоста одинаковые шесть полей. Откат убирает только ключи паддинга из инбаунда и хостов; если их правили после KERBEROS, показывает diff и спрашивает, а после согласия убирает паддинг и у изменённых инбаундов, чтобы сервер и клиенты остались согласованы. Клиенты со старой подпиской через этот инбаунд не подключатся, пока не обновят её: S7 предупреждает дословно `fix.padding.warning`.
- **`cdn.edge_only`.** Для origin под nginx с распознанной раскладкой (location пути туннеля с proxy_pass на Xray). Агент `edge-sources` собирает сети /24, с которых шли запросы к пути туннеля; S7 показывает их, человек подтверждает список. Дальше конфиг, стоящий на парке: `conf.d/kerberos-edges.conf` с `geo $from_cdn_edge` (127.0.0.1, IP самой ноды, подтверждённые сети); сниппет `error_page 418 = @kerberos_not_edge; if ($from_cdn_edge = 0) { return 418; }` сразу после `{` location пути туннеля и `/cdn-check` (так работает и location в одну строку); именованный location с тем же ответом, что у сайта на несуществующий путь. Нужен именно `if` с `return 418`: `return` срабатывает раньше `allow/deny`. При включённом `realip` агент отказывает (`realip_enabled`): адрес клиента подменился бы, и фильтр отрезал бы всех. Перепроверка: прямой запрос даёт тот же ответ, что несуществующая страница; запрос через edge работает.
  - Параметры агента: `{paths, nets}` — пути туннеля всех CDN-хостов ноды и подтверждённые сети. Агент ищет `real_ip_header` и `set_real_ip_from` в `sites-enabled`, `conf.d` и `nginx.conf`. Если файл сайта в `sites-enabled` — ссылка (обычно на `sites-available`), агент правит файл, на который она указывает; ссылка остаётся. Именованный location отвечает `return 404`. Откат возвращает файл сайта, удаляет `kerberos-edges.conf` и перезагружает nginx.
  - S7: строка фильтра не отмечена, пока человек не подтвердил сети. Клавиша `e` вызывает `edge-sources` для каждого пути и показывает сети /24 с числом запросов списком с отметками (отмечены все); Enter подтверждает отмеченные. Пустой список — фильтр не применяется (не из чего собрать сети). `a` строку без подтверждённых сетей не отмечает. При `realip` в фактах строка заблокирована. Предупреждение до согласия дословно `fix.edge_only.warning`.
  - Перепроверка подробно: с сервера панели на каждый TLS-порт сайтов nginx (`tls_listen_ports`) прямой запрос к пути туннеля и к `/cdn-check` должен дать тот же статус и тело, что случайный несуществующий путь; затем запрос к пути туннеля через адрес CDN-хоста (edge) должен ответить иначе, чем несуществующая страница. Иначе (в том числе если edge не в списке и CDN получила ответ несуществующей страницы) изменение откатывается с `recheck_failed`.

### 10.7 Практика против методички
Методичка «Комплексный разбор методик защиты VPN-серверов от блокировок ТСПУ» в нескольких местах расходится с практикой. KERBEROS следует практике:
- `scMaxEachPostBytes: 1200` через CDN не ставится: на реальных объёмах это умножает число запросов к edge и упирается в лимит 150–256 запросов на соединение. Проверено на трёх CDN.
- Фрагментация ClientHello и MTU 1280 не применяются: при self-steal SNI совпадает с IP, резать нечего; MTU — настройка клиента, а не сервера.
- ICMP на ноде не выключается. На поведение влияет тип пинга клиента (`client.ping_type`), а ping ноды нужен для диагностики.
- Принудительный разрыв соединений раз в несколько часов не применяется: замер на четырёх нодах показал, что 96 % соединений Reality закрываются сами за час, дольше 8 часов живут меньше 1 %. Ротация соединений к CDN уже есть в xmux (`hMaxReusableSecs`).

### 10.8 Бэклог
`site.alt_svc` (Hysteria2 есть, а сайт не объявляет `Alt-Svc: h3`), `reality.empty_shortid` (пустой shortId первым), `hy2.obfs`, `sub.hidden_reserves` (скрытые резервы видны в JSON-подписке), `node.torrents`, проверка IP из РФ через внешние сканеры, отправка отчёта в Telegram ботом панели (§23, Q3), английский интерфейс, копии хостов self-steal сразу после исходных (`POST /api/hosts/actions/reorder`, §23 Q4), удаление созданных шаблонов при откате (`DELETE /api/subscription-templates/{uuid}` в панели есть).

| Метка | Чем заменяется |
|---|---|
| `__REALITY_TAG__`, `__HY2_TAG__` | тег существующего инбаунда того же типа в профиле ноды; если инбаунда нет или нода получает свой профиль (§10.4), `VLESS-REALITY-<NODE>` и `HY2-<NODE>`, где `<NODE>` — имя ноды латиницей в верхнем регистре; при совпадении с тегом другого профиля панели — с `-2`, `-3`: тег инбаунда уникален на всю панель (§7.4) |
| `__REALITY_PRIVATE_KEY__`, `__REALITY_SHORT_ID__` | существующие ключ и shortId Reality ноды; если Reality не было, новая пара x25519 и случайный shortId из 16 hex |
| `__DOMAIN__` | домен ноды из self-steal |
| `__SERVER_NAMES__` (элемент списка) | `[<домен>, <старые имена>]` до финализации, `[<домен>]` после |
| `__OWN_DOMAINS__` (элемент списка) | `domain:<зона>` для каждой DNS-зоны доменов нод панели |

После подстановки в файле не остаётся ни одной метки; иначе KERBEROS ничего не пишет и показывает ошибку.

**Профиль ноды.**
- Сохраняются: теги Reality и Hysteria2 (по ним панель держит uuid инбаундов, хосты и сквады), приватный ключ и shortId Reality.
- Остаются как были: прочие инбаунды пользователя (XHTTP за CDN, paywall и другие) и правила `routing` с `inboundTag` этих инбаундов; они встают перед правилами шаблона. Отчёт перечисляет, что сохранено.
- Новый инбаунд (например, Hysteria2, которого не было) добавляется во все внутренние сквады, где есть Reality-инбаунд ноды (`PATCH /api/internal-squads {uuid, inbounds}`), иначе пользователи его не увидят, и включается на самой ноде (`activeInbounds`, §10.4), иначе панель его не запустит. Снимок сквадов до изменения; откат читает сквад заново и убирает только добавленные KERBEROS инбаунды (`details.added`), инбаунды, добавленные позже, остаются.
- Профиль, общий для нескольких нод, не меняется: нода получает свой (§10.4).

**`node.letsencrypt_mount`** **[новое].** Hysteria2 читает сертификат из `/etc/letsencrypt/live/<домен>/` внутри контейнера ноды. Если тома нет (`facts.remnanode.letsencryptMounted = false`; агент смотрит `Mounts` в `docker inspect` контейнера, а не текст compose), агент добавляет `/etc/letsencrypt:/etc/letsencrypt:ro` в `volumes` сервиса ноды в `/opt/remnanode/docker-compose.yml` (бэкап файла; элементы списка на уровне `volumes:` и длинная форма остаются верным YAML) и выполняет `docker compose up -d`. Если compose уже называет этот том, файл не пишется, выполняется только `docker compose up -d`. Нода переподключается к панели за секунды; S7 предупреждает об этом. Откат: прежний compose и `docker compose up -d`.

**Шаблоны в панели.** KERBEROS создаёт два шаблона XRAY_JSON, `KERBEROS` и `KERBEROS single` (в имени шаблона панель разрешает только латиницу, цифры, пробел, `_` и `-`; `POST`, затем `PATCH` содержимого), или обновляет их, если они уже есть. Перед обновлением снимок; если содержимое в панели правили руками, KERBEROS показывает diff и спрашивает.

**Резерв.** В S7 у каждой основной ноды выбор «Резервная нода»:
- **другая нода панели.** Резерв тоже должен быть защищён этим же запуском (свой домен, свой профиль). Связывание пары пишет что-либо, только если у обеих нод self-steal прошёл и копии хостов есть, иначе `pair_not_ready`. Цепочки и общий резерв запрещены: нода, которая уже чей-то резерв, своего резерва в S7 не получает, а изменение `reserve` отказывает с `reserve_chain`. Хосты основы и резерва получают общие теги пары, по одному на протокол: `KRB_<NODE>_VLESS`, `KRB_<NODE>_HY2` (формат тега панели `^[A-Z0-9_:]+$`, до 32 символов, как берут и 2.2–2.7: `<NODE>` длиннее 22 символов укорачивается до 17 и получает `_` и 4 символа хэша имени ноды). Хосты основы: видимые, шаблон `KERBEROS`. Хосты резерва: `isHidden = true`, тот же шаблон; если у резерва нет хостов, KERBEROS создаёт их по образцу хостов основы с адресом и доменом резерва. Шаблон с резервом вставляет скрытые хосты с тем же тегом как outbound `reserve`, клиент уходит на них, когда проба основы не проходит. Основа и резерв в одной AS дают находку `reserve.same_asn`.
- **«Без резерва».** Хосты ноды получают шаблон `KERBEROS single` и не получают тегов пары. Находка `reserve.missing` остаётся в отчёте.

Откат резерва: прежние `tags`, `isHidden` и `xrayJsonTemplateUuid` хостов из снимка, удаление созданных хостов резерва.

### 10.10 Портал перед панелью

Решения владельца (v20): у Remnawave перед панелью встаёт портал входа caddy-security, у 3x-ui включаются её собственные секретный путь и случайный порт. Оба исправления меняют, как человек входит в веб-интерфейс панели, поэтому в S7 они не отмечены по умолчанию и `a` их не отмечает. После переключения KERBEROS просит войти по новой ссылке из браузера: не вышло или нет ответа 180 с — всё возвращается.

**`panel.portal` (Remnawave).** Условие — схема из документации Remnawave: Caddy в Docker перед панелью.
- Поиск (только чтение, S5): сервер amd64 (образ собран только для него; на другой архитектуре `evidence.proxy` — `arch`); контейнер, чей образ содержит `caddy`; Caddyfile смонтирован с хоста в `/etc/caddy/Caddyfile`; метки compose дают каталог, файлы, проект и сервис. В Caddyfile ровно один блок сайта с доменом панели (`PANEL_DOMAIN`), где кроме `reverse_proxy <адрес панели>` одной строкой только `encode`, `header`, `log` и комментарии; в глобальных опциях нет `order` и `security`; нет `import` и `tls` с файлами (контейнер проверки их не видит); на сервере есть `docker compose` (плагин). Caddyfile, где уже есть `security`, `authenticate`, `authorize`, `forward_auth` или `basic_auth`, KERBEROS не трогает. Иначе находка остаётся ручной, `evidence.proxy` говорит почему: `none` (Caddy в Docker нет), `custom` (Caddyfile не по схеме) или `arch`. Сгенерированный Caddyfile проверен на Caddy 2.9.1 с caddy-security 1.1.27: корень, интерфейс и `/api` без токена уходят на `/restricted`, подписки и API с токеном доходят до панели.
- Применение:
  1. `docker pull remnawave/caddy-with-auth:0.0.1` (Caddy 2.9.1 с caddy-security 1.1.27). Не скачался — ничего не меняется (`image_pull_failed`).
  2. Новый Caddyfile. Глобальные опции получают `order authenticate before respond`, `order authorize before respond` и блок `security`: локальное хранилище пользователей `/data/.local/caddy/kerberos-<changeId8>.json` (у каждого изменения своё: администратор заводится из окружения только в пустом хранилище), портал `kerberosportal` с `require mfa`, политика `kerberospolicy`. Блок панели становится одним `route`: портал по секретному пути (`/{$REMNAWAVE_CUSTOM_LOGIN_ROUTE}`), `/restricted*` обрывает соединение, `/api/*` с заголовком `Authorization: Bearer` (кроме `/api/auth/*`: вход и статус панели остаются за порталом) и `/api/sub/*` идут в панель мимо портала, всё остальное — только после входа в портал. Прочие блоки и опции Caddyfile остаются как были. Рядом с compose файл `kerberos-portal.env` (0600): домен, секретный путь (18 строчных латинских букв и цифр), `AUTHP_ADMIN_USER`, `AUTHP_ADMIN_SECRET`, `AUTHP_ADMIN_EMAIL` (`<логин>@localdomain.local`), время жизни входа 3600 с. Новый Caddyfile проверяется тем же образом (`caddy validate`) до замены: не прошёл — `caddy_invalid`.
  3. Бэкап Caddyfile и compose (байты и права) в `runs/<runId>/panel-server/` (0600). Затем запись: Caddyfile, env, а в compose у сервиса Caddy образ `remnawave/caddy-with-auth:0.0.1` и `env_file` с `kerberos-portal.env`. `docker compose config -q` (не прошёл — файлы назад, `compose_invalid`), `docker compose up -d <сервис>`.
  4. Проверка с сервера панели, до шести раз по 5 с: корень домена больше не отдаёт страницу Remnawave, страница входа портала `/<путь>/auth/login` отвечает 200 (сам секретный путь переадресует на неё), `/api/sub/<случайное>` отвечает тем же кодом, что до изменения, `GET /api/nodes` с API-токеном через домен отвечает 200. Не прошла — откат (`portal_check_failed`).
  5. S8 просит открыть ссылку портала в браузере, войти и завести второй фактор: Enter — вошёл, Esc или 180 с без ответа — откат (`portal_login_failed`). Ctrl+C тоже откатывает портал и останавливает запуск; `q` на этом вопросе не выходит из KERBEROS. При маскировке экран скрывает секретный путь и называет снимок 0600, где ссылка целиком.
- Логин (3–50 строчных латинских букв и цифр) и пароль (от 8 символов, дважды) вводятся в S7 клавишей `p` у строки и живут в памяти до записи env. В `run.json` и отчёт они не попадают. Секретный путь лежит в env и в снимке `runs/<runId>/panel/portal-<changeId8>.json` (0600), в `run.json` только путь к снимку. S9 и `report.md` показывают ссылку портала, при маскировке она скрыта.
- Откат: Caddyfile и compose из бэкапа (если их правили после KERBEROS — diff и вопрос), env удаляется, `docker compose up -d <сервис>` (только если KERBEROS успел перезапустить Caddy). Любая ошибка KERBEROS на этих шагах (`internal_error`) откатывается так же. `kerberos rollback` откатывает `panel.portal` и `xui.panel_hide` последними: остальные изменения панели запуска идут через её текущий адрес.

**`xui.panel_hide` (3x-ui).** Условие: находка `xui.panel_exposed`, база SQLite найдена (§7.6).
- Новый порт — случайный из 20000–32767, не занятый по фактам агента; если порт задан `XUI_PORT` в `/etc/default/x-ui`, он не меняется. Новый путь — 18 строчных латинских букв и цифр, если пути не было; существующий секретный путь остаётся.
- Применение: `x-ui setting -port <порт> -webBasePath /<путь>/` (с `XUI_DB_FOLDER` из `/etc/default/x-ui`); ссылка для человека называет `webDomain`, если он задан (иначе 3x-ui ответит 403), иначе IP сервера. Команда печатает ошибки, но выходит с кодом 0, поэтому KERBEROS перечитывает настройки из базы (`xui_setting_failed`). Если ufw активен — `ufw allow <порт>/tcp`. Веб-сервер панели перезапускается сигналом HUP главному процессу `x-ui`: Xray не перезапускается, клиенты не отключаются. Проверка: панель отвечает по новому адресу с той же сессией KERBEROS (кука с путём `/` годится и для нового пути), иначе откат (`portal_check_failed`). S8 просит войти со своего компьютера по новой ссылке: Enter — вошёл, Esc или 180 с — откат (`portal_login_failed`). Если у хостера свой фаервол, новый порт нужно открыть в нём (`fix.xui_hide.warning`).
- Откат: прежние порт и путь той же командой, правило ufw удаляется, HUP.
- 2FA и TLS панели остаются ручными (`xui.panel_2fa`, `xui.panel_tls`): для 2FA нужно отсканировать QR-код в панели, для TLS нужен сертификат на домен.

## 11. Изменения, бэкапы и откат

### 11.1 Запуск
Каждый запуск получает `runId` (время UTC и 4 случайных символа, `20261116T123456Z-a1b2`). Запуск в режиме «Проверка» пишет только находки и отчёт.

### 11.2 Изменение
Изменение: одно исправление на одной цели (нода, профиль, шаблон, хост). Жизненный цикл: `planned → applying → applied | pending_confirm → confirmed | failed | rolled_back`. Журнал пишется до каждого перехода: прерванный процесс оставляет честное состояние.

### 11.3 Подтверждение доступа
`pending_confirm` снимается только `confirm` по новому соединению KERBEROS. KERBEROS ждёт до 60 с; не вышло: вызывает `rollback`, а если и он не дошёл, нода откатится сама по таймеру агента.

### 11.4 Откат
`kerberos rollback` показывает запуски, их изменения и состояние; откат идёт в обратном порядке. Если изменение ноды не откатилось, более ранние изменения этой ноды не откатываются (`rollback_skipped`): они могли от него зависеть; остальные ноды откатываются. Откат подтверждённого `ssh.port` подтверждается новым соединением на старый порт в течение 60 с (§9.3; на 3x-ui вход снаружи делает человек, как при применении). Не вышло: агент возвращает новый порт, изменение остаётся `confirmed` с ошибкой `port_closed`, код выхода 5. Итог отката показывает сбои, что проверить руками и путь к отчёту текстом. Запуск отката (`mode: rollback`) получает `scoreBefore` = `scoreAfter` откатываемого запуска и `scoreAfter` = его `scoreBefore`, без новой проверки (при частичном откате это оценка снизу). Запуски в списках отката и отчётов подписаны датой, режимом, числом изменений или оценкой и именами нод: «16.11.2026 12:00 UTC · Исправление · изменений: 19 · nl-1, nl-2, …». Изменение в панели перед откатом сравнивает текущий объект с записанным после применения; при расхождении показывает diff и спрашивает. Удачный откат: `rolled_back`; неудачный: код выхода 5 и в отчёте, что проверить руками.

### 11.5 Прерывание
`Ctrl+C` во время применения спрашивает «Прервать?». Изменение, которое уже идёт, доводится до конца или откатывается; новые не начинаются. После прерывания запуск выдаёт отчёт с тем, что успело измениться.

### 11.6 Идемпотентность
Повторный запуск «Исправления» на уже исправленном парке ничего не меняет: проверки проходят, план пуст. Повторный `apply` агента с тем же `changeId` возвращает `noop`. Повторная вставка правил в шаблон не дублирует их.

## 12. Отчёт

### 12.1 Где
На экране (S6, S9) и в файлах `runs/<runId>/report.md` (читается человеком) и `report.json` (модель §13). Путь печатается в конце. `kerberos report` показывает последний отчёт.

### 12.2 Оценка
Оценка 0–100: сумма весов пройденных проверок к сумме весов применимых. Веса: высокий 10, средний 5, низкий 2, инфо 0. Красный до 59, жёлтый 60–84, зелёный от 85.

### 12.3 Содержание
- шапка: время, режим, панель (Remnawave или 3x-ui) и версия, число нод, оценка (в «Исправлении» до и после);
- хосты и шаблоны названы по именам из панели, а не по uuid; изменение, которое не применилось и не откатилось, помечено «не откатилось»;
- находки по темам §10.2: риск, нода, что не так, чем грозит, что сделано или что сделать вручную; в «Исправлении» — находки после него (`findingsAfter`), как оценка после и S9: что исправлено, видно в списке изменений;
- таблица нод: адрес, порт SSH, на котором нода отвечает после запуска (новый после `ssh.port`, прежний после его отката), доступ;
- по каждой ноде: применённые изменения, новый порт SSH, новые отпечатки ключей хоста, бэкапы на ноде, как войти теперь (`ssh -p <port> root@<addr>` или `kerberos ssh <нода>`);
- в панели: какие хосты созданы и какие выключены, какие шаблоны изменены;
- отложенное: финализация self-steal и когда;
- откат: `sudo /opt/kerberos/kerberos rollback <runId>`.

В отчёте нет паролей, токенов, приватных ключей, ключей Reality, UUID и email пользователей, ссылок подписки. Файлы 0600. `--mask` маскирует адреса и домены и в файлах.

### 12.4 Видео
Сценарий для записи: `--demo --mask` или живой парк с `--mask`. S6 с красной оценкой → S7 → S8 → S9 с оценкой после исправления. В демо оценка растёт с 38 до 77 (жёлтая): находки, которые исправляются только руками, оставлены в демо-парке нарочно (решение владельца, v14); зелёный финал снимается на живом парке после ручных шагов из отчёта. Сцены, клавиши и подписи — в `docs/video.md`; кадры для README собирает `tools/screenshots.py` в `docs/screens/`. Экраны должны читаться на видео при ширине терминала 100 колонок.

## 13. Модель данных

Контракты `run.json` и `report.json` (Python TypedDict в `kerberos/fixes/model.py`):

```python
Risk = Literal['high', 'medium', 'low', 'info']
Topic = Literal['hosting', 'sni', 'scanning', 'dpi', 'routing', 'reserves']

class Finding(TypedDict):
    checkId: str
    topic: Topic
    risk: Risk
    target: str                        # 'node:<uuid>' | 'panel' | 'fleet' | 'template:<uuid>' | 'host:<uuid>'
    ok: bool
    evidence: dict                     # short machine facts, no secrets
    fixId: str | None                  # None: manual or info

class Change(TypedDict):
    changeId: str                      # uuid4
    fixId: str
    target: str
    state: Literal['planned', 'applying', 'applied', 'pending_confirm', 'confirmed',
                   'failed', 'rolled_back']
    params: dict                       # e.g. {domain, reserveNodeUuid | None} for self_steal, {port} for ssh.port
    before: str | None                 # path of the panel snapshot in runs/<runId>/panel/
    details: dict                      # agent details, created host uuids, new port, fingerprints
    error: str | None                  # error code from §9.2 or §7.5, or of KERBEROS itself:
                                       # confirm_failed, recheck_failed, port_closed, check_failed,
                                       # node_offline, host_mismatch, changed_in_panel,
                                       # rollback_skipped (an earlier change of a node whose later
                                       # change did not go back), rollback_failed (see below),
                                       # internal_error, pair_not_ready, reserve_chain,
                                       # hostkey_mismatch, node_mismatch, profile_in_use
    startedAt: str
    finishedAt: str | None

class Run(TypedDict):
    runId: str
    mode: Literal['check', 'fix', 'rollback', 'finalize']
    kerberos: str                      # version
    panel: dict                        # {version, nodes, hosts, api, kind: 'remnawave' | '3x-ui'}
    nodes: list[dict]                  # {uuid, name, address, sshPort, access: 'ok' | 'none' | 'denied',
                                       #  accessReason?: why there is no access, text of §6 S4}
    findings: list[Finding]
    changes: list[Change]
    scoreBefore: int
    scoreAfter: int | None
    pending: list[dict]                # {changeId, action: 'finalize', due}
    startedAt: str
    finishedAt: str | None
    # optional: findingsAfter (findings after «Исправление»), interrupted (Ctrl+C),
    # rolledBackRun (mode 'rollback': the run whose changes went back),
    # finalizeTimer (unit name, only when the timer was really set)
```

Изменение, у которого не прошёл и автоматический откат (`error = rollback_failed`), остаётся в том состоянии, до которого дошло (`applying`, `applied`, `pending_confirm`, `confirmed`): оно, возможно, на месте. `details.failure` — исходная причина (`recheck_failed`, `confirm_failed`, вид сбоя транспорта, код панели), `details.rollbackError` — почему не прошёл откат. Такие изменения и оборванные на середине (`applying`) перечисляет `kerberos rollback`; удачный откат ставит `rolled_back`, а в `error` возвращает исходную причину; неудачный оставляет `rollback_failed` и пишет новую причину в `details.rollbackError`. Изменение `applying`, о котором агент ничего не знает (`no_backup`), считается откаченным. S8 и S9 пишут о таких изменениях «не применилось и не откатилось», отчёт — «не откатилось», запуск выходит с кодом 5.

Поля `details` портала (§10.10): `panel.portal` — `container`, `service`, `project`, `composeDir`, `composeFiles`, `caddyfile`, `envFile`, `image`, `backups` (пути бэкапов), `written` (sha256 записанных Caddyfile и compose), `linkPath` (снимок с секретным путём, 0600); `xui.panel_hide` — `oldPort`, `newPort`, `pathChanged`, `ufw`, `linkPath` (снимок с прежним и новым путём, 0600).

Новые поля `details`: `self_steal.site` — `renewals` (`[{tool, name, names}]`: продления, переведённые на nginx, §10.4); `self_steal.profile` — `tags` (`{reality, hysteria}`), а после финализации `written`/`writtenPath` (`panel/profile-<uuid>-final.json`, 0600); `self_steal.own_profile` — `profileUuid`, `name`, `sharedUuid` (прежний профиль ноды или null), `tags`, `written`, `writtenPath` (0600: в профиле ключ Reality); `self_steal.squads` — `squads` (сквады до изменения) и `added` (список инбаундов; в журналах до v29 — один uuid); `self_steal.node` — `profileUuid`, `before` и `added` (инбаунды ноды до изменения и включённые KERBEROS), у своего профиля ещё `beforeProfile`; `sub.template` — `written` (`{host: template}`); `reserve` — `written` (`{host: fields}`); `sub.templates` — `writtenPath` у каждого шаблона.

## 16. Безопасность и приватность

- Пароль и сессия 3x-ui живут только в памяти процесса. API-токен Remnawave хранится в `/var/lib/kerberos/panel.token` (0600, решение владельца, v19): root сервера панели и так управляет панелью, её секреты лежат в `.env`. Пароль ноды KERBEROS не видит: его читает `ssh` из терминала. Логин и пароль портала перед панелью (§10.10) лежат в `kerberos-portal.env` рядом с compose Caddy (0600): так их берёт образ; в журнал, `run.json` и отчёт они не попадают.
- Приватные ключи KERBEROS и администратора 0600 в `/var/lib/kerberos/`; каталог 0700.
- Журнал и отчёт не содержат секретов (§12.3). Тест проверяет отсутствие паролей и токенов в файлах запуска.
- Ключ KERBEROS на нодах ограничен `from=` и `command=` (§8.4).
- KERBEROS не меняет доступ к серверу панели, на котором работает человек.
- Внешние запросы: только whois после согласия. Никаких отчётов наружу, телеметрии и проверок обновлений.
- Риск: захват сервера панели даёт злоумышленнику команды агента на нодах, а через `access.admin_keys` и `update` фактически root на них (§8.4). Сама панель и так управляет нодами, поэтому сервер панели защищается не хуже нод.

## 17. Тесты

Тесты выводятся из критериев приёмки задачи, а не из реализации: тест кодирует контракт и не повторяет код. Задача без тестов не готова.

Обязательно:
- **Шаблоны.** Тест сравнивает `templates/*.json` с эталонными хэшами: случайная правка проверенного конфига ломает сборку. `subscription-single.json` совпадает с `subscription-reserve.json` за вычетом балансировщика, `injectHosts`, `burstObservatory` и правил на `se-auto`.
- **Контрактные на стыках.** Клиент панели против фикстур обеих форм хоста (`tags` и `xhttpExtraParams`, `tag` и `xHttpExtraParams`), ответов `auth/status`, `bulk/disable` (и 204 без тела), прав API-токена. JSON агента: pytest собирает вывод из записанных `ss`, `sshd -T`, `nft list`, `systemctl` и сверяет с `tests/fixtures/agent/*.json`. Фейк панели и фейк транспорта проверяют вход по контракту и падают на мусоре.
- **Идемпотентность.** Повторный `apply` агента с тем же `changeId` даёт `noop`; повторное «Исправление» на исправленном фейковом парке даёт пустой план; вставка правил в шаблон идемпотентна; повторная финализация ничего не меняет.
- **Путь ошибки через фейки.** Панель 401, 403, 500, таймаут, POST без ответа; SSH таймаут, отказ, смена ключа хоста; агент с кодом ошибки; сбой на каждом шаге self-steal с откатом сделанного; `confirm` не дошёл, таймер откатил; прерывание `Ctrl+C` на каждом шаге.
- **Property-based (Hypothesis).** После подстановки в шаблоны §10.9 не остаётся меток, теги и ключи Reality сохраняются, чужие инбаунды и их правила не теряются; подстановка идемпотентна; копия хоста отличается от исходного только полями §10.4; оценка §12.2 не падает, когда проверок проходит больше; маскировка детерминирована и не оставляет исходных октетов и доменов; разбор `ss` не падает на случайных строках; случайный порт SSH всегда в диапазоне и не занят.
- **Агент.** Функции агента принимают корень файловой системы и исполнитель команд параметрами; pytest проверяет файлы, откат до прежних байтов и прав, строку таймера.
- **Экраны.** Сценарии клавиш через фейковый терминал проходят S1–S9 в `--demo`; снимки текста S6 и S9 при ширине 100 сравниваются с эталонами в `tests/snapshots/`.
- **Стенд.** Задачи с изменениями на нодах проверяются на одноразовых VM (Ubuntu 22.04, 24.04, 26.04, Debian 12, 13) и тестовой панели Remnawave: применить, откатить, повторить. Боевые серверы владельца для разработки не используются.

## 18. Проверки и релизы
GitHub Actions не используются. Проверки запускаются локально:
- `tools/check.sh` на машине разработчика: ruff; pytest на Python 3.9 и 3.14 через `uv run --python <версия>` (крайние версии из §3.1); тест запуска `python3 -I -S` с одним `vendor/`; проверка хэшей `templates/`. Запускается перед каждым коммитом в PR.
- `tools/stand.sh` для задач, которые трогают агента или исправления на нодах: копирует агента и его тесты на пять VM стенда (Ubuntu 22.04, 24.04, 26.04, Debian 12, 13), гоняет там pytest агента и сценарий «применить, откатить, повторить», собирает итог в один отчёт. Если на машине разработчика есть Docker, тот же pytest агента можно прогнать в контейнерах этих ОС (`tools/stand.sh --docker`); сценарий на стенде это не заменяет. VM стенда могут быть и локальными (Lima на машине разработчика); `tools/stand.sh` ждёт cloud-init и обновляет списки пакетов перед установкой pytest. Сбой копирования, домена или cloud-init на одной VM записывается в отчёт, остальные VM проверяются дальше. Сценарий проверяет каждый порт SSH баннером sshd по новому соединению (новый порт до `confirm`), проходит двухфазный откат порта через `undo` и до конца, а на Ubuntu 22.04 ещё раз с включённым ufw.
- Итог обоих скриптов вставляется в описание PR.
- Релиз: тег `vX.Y.Z` на main; README на русском со скриншотами только в маскировке.

## 24. Проверено на практике

Факты с живого парка автора, ноябрь 2026, без адресов. На них основаны пометки **[парк]**.
- До `ssh.key_only` на нодах было от 5 до 23 тысяч неудачных попыток пароля за сутки на каждой. После: входов по паролю нет, fail2ban банит перебор.
- Чужой SNI на IP хостинга: одна нода заблокирована через 1–2 минуты после запуска, три IP одной страны за пять дней. После self-steal этот вектор закрыт, но блокировки по IP продолжаются: новая основа на своём домене ушла в блок примерно через 42 часа.
- Полная блокировка (SYN не доходит) не видна по срезу соединений: её показывает обвал пользователей ноды при живом резерве. Отсюда условие `node.blocked`.
- Порт 2222 с правилом «только панель» на десяти нодах: панель ни разу не переподключилась, счётчик accept 76–88 пакетов за 25 секунд.
- Origin за CDN после `cdn.edge_only`: прямые запросы получают ответ несуществующей страницы, туннель через edge работает, пользователи изменения не заметили.
- Российский трафик через ноды после `sub.ru_direct`: от 0 до 9 соединений из 38–81 тысячи.
- 96 % соединений Reality живут меньше часа, дольше 8 часов меньше 1 % (замер на четырёх нодах).
- `POST /api/auth/login` в панели есть, но токен входа администратора она принимает только от своего веб-интерфейса (заголовок `X-Remnawave-Client-Type: browser`), программе отвечает 403: найдено первым запуском KERBEROS на живой панели (v19). Программы входят по API-токену с правами по разделам.
- Конфиги из `templates/` работают на живом парке: профиль на нодах с self-steal, шаблон с резервом на парах основа–резерв (переключение проверено обрывом основы), шаблон без резерва на одиночных нодах.
